## Последовательность

1. Сохранить исходный Release ELF/BIN/map и хеши всех ASM; сборки и промежуточные файлы только в `%TEMP%`. Исходная сборка прошла: 0 ошибок, одно Ls016.
2. Перенести 11 эталонов в User/c с сохранением ABI/данных. Сначала сравнить неизменённые модули, затем обновить разошедшиеся функции. Ручные автоматы и ядра перевести на обычный C. CMSIS/IAR intrinsics применять только для необходимых процессорных операций IRQ, без ASM-вставок.
3. Добавить проекты ASM и C с общими исходниками, Release High/Size; C ReleaseSpeed High/Speed. Старый проект сохранить. Проверить PUBLIC-набор, размеры структур, секции и адреса/смещения runtime_layout.
4. Параметризовать harness выбором исходников и ELF, не подменяя текущую логику устаревшим эталоном. Прогнать host/regression, ELF-сценарии, мутации. Сопоставлять ответы, журнал и NOR с одинаковыми входами; power-cut и ошибки входят в проверку.
5. Собирать команды Unicorn отдельно от расчётной оценки циклов. LATENCY=2 не делает каждую команду равной 3 тактам: учитывать prefetch/ветвления и явно описать ограничения модели. Измерения платы не заявлять.
6. Сверить исходный/итоговый ASM ELF, сформировать размер по map, сравнение по функциям/путям и отчёт Tests/C_VS_ASM_20261006.md. Не больше пяти итоговых c_vs_asm_*.json.

## Оценка и границы

Объём: около 40 тыс. строк ASM, около 8 тыс. строк существующего C, восемь модулей без отдельного эталона; наибольший риск — ручные автоматы, heap/отмена/IRQ и связки user_fun. Это многоэтапный перенос, а не механическое копирование: ориентир 40–70 инженерных часов с полным набором проверок. Фактическое выполнение и незакрытые пункты фиксируются в итоговом отчёте.

Стоп-условие для каждого модуля: после трёх неуспешных подходов к совпадению оставить исходный ASM в обоих проектах, записать три результата и не выдавать смешанную сборку за полностью C. Ошибки исходной логики документировать без молчаливого исправления. Функциональность и разделы не урезать ради размера.

# Старт без полного чтения ID — 13.10.2026

База: `59c3d43`, worktree `domovoi-exec`, ветка `task/exec`.
Плата №1 не прошивалась, сервер не затрагивался, `compare/c-asm` не перемещалась.

## Решение и сравнение

Выбран вариант **б**: полный проверочный проход остаётся, но выполняется главным
циклом по 256 Б. Сумма базы сверяется с отметкой только после последней страницы.
Таким образом, сохраняется прежняя защита от незавершённой записи и изменений
старой прошивкой; доверия к сохранённым счётчикам не добавлено.

Вариант **а** рассмотрен, но не реализован. Сейчас `idindex_runtime_suspend`
гасит готовность только в ОЗУ: долговечной отметки «база изменяется» перед каждой
записью базы нет. Для доверенного старта пришлось бы добавить её во все пути,
включая прямую допись, секторный журнал, очистку, factory/recovery. При погашенной
отметке для быстрого старта всё равно нужен фоновый проход и те же запреты записей.
Нужно также согласованно публиковать счётчики после каждого пути изменения базы.

| Сравнение | а: доверенная отметка | б: выполнено |
|---|---|---|
| Отметка NOR | минимум 16 Б с общей контрольной суммой; 24 Б при попарной инверсии полей | прежние 8 Б, новая версия проверки |
| Дополнительные поля | число 2 Б, граница 2 Б, занятый хвост 4 Б, их проверка | нет |
| Запись перед изменением базы | обязательное проверенное долговечное погашение | соответствие проверяется полным чтением при каждом старте |
| Старт при погашенной отметке | проход всё равно необходим | одинаковый путь при любой отметке |
| Поиск в последней ячейке | READY: 96 Б, 0,116–0,268 мс | до конца прохода: 1 601 536 Б, 1 587,639–3 647,260 мс |
| Полное обслуживание первой карты | READY: 208 Б, 0,265–0,613 мс после инициализации | 1 601 616 Б, 1 587,497–3 646,927 мс после инициализации |
| BIN / статическая ОЗУ | не собирался; размер кода не выдаётся за замер | +380 / +12 Б |

Время READY измерено на том же связанном коде с подготовленной корзиной; это
сравнение путей доступа, а не измерение несуществующей реализации старта варианта а.
Быстрее до первой карты был бы вариант а с верной отметкой. Вариант б выбран за
единый способ восстановления и отсутствие нового долговечного протокола записи.

## Изменения и инварианты

- `User/c/user_ids.c:194`: вместо `user_getNumbersCount` — `user_ids_boot` без
  чтения NOR. До завершения прохода `id_cells_end` равна ёмкости всей области,
  `id_used_bytes=UINT32_MAX`, индекс не READY.
- `User/c/user_ids.c:204`: одна страница за квант; ошибка повторяет эту страницу,
  не теряет префикс и не удваивает счёт. Последняя непустая физическая ячейка
  определяет занятый хвост, последняя живая — границу поиска. Число живых ID,
  границы и XOR публикуются согласованно перед допуском записей/CRC/статуса.
- `User/c/user_ids.c:92,120`: при стартовом проходе сохраняется только номер
  последней найденной ячейки. Повтор проверяет её 32 Б и сравнивает сам ID;
  другой ID требует обычного поиска. Нет копии записи и нет доверия к одному
  хешу. Это убирает повторные полные чтения в ready → проверка → счётчик доступа
  и позволяет карте со счётчиком ждать, не тормозя каждую следующую страницу.
- `User/c/user_config.c:58`: запуск фонового прохода после `user_comm_boot`.
- `User/storage_profile.c:37`, `User/c/idindex_runtime.c:104`: используется
  существующий исполнитель INDEX; проход доступен и на W25 2 МиБ без индекса.
  Новый вид работы, очередь или постоянный буфер не добавлены.
- `User/c/user_store.c:232`: зависимые команды 3/13/17/18/101/103 ждут; USB/сервер
  сохраняют принятый кадр. Остальные команды используют прежний допуск.
- `User/c/user_protocol.c:311`: частичное число ID не попадает в статус 101.
- `User/c/table_runtime.inc:84`, `User/c/store_io.inc:4`,
  `User/c/expiry_runtime.c:47`, `User/c/idclear_runtime.c:46`,
  `User/c/factory_runtime.inc:35`: владельцы не принимают изменение базы до
  готовности стартовых данных. `User/c/user_access.c:446` удерживает карту,
  которой понадобится запись счётчика/начала срока; обычный доступ разрешён.
- `User/id_crc_cache.c:40,123`, `User/c/service_runtime.c:54`: физическая запись
  ID и расчёт CRC ждут готовых границ; частичный хвост не принимается за FF.
- `User/c/idindex_runtime.c:20`: проверка отметки `IX_MAGIC` меняется
  `0x58444931 → 0x58444932`. Размер 8 Б и область 0x340000 сохраняются. Старые
  отметки требуют одной пересборки; следующие старты принимают новую отметку
  после проверки базы. Сами ID не мигрируют и не стираются.
- `Tests/check.py:29`, `Tests/run_all.py:135`: явно заданный PYTHONPATH имеет
  приоритет над общим TEMP. Зависимости установлены только в
  `build/id-startup/deps`; `%TEMP%/codex-deps` не изменялся и не использовался.

Запрет на запись действует для рабочих команд после старта. Прежний синхронный
`mem_recover` до `user_ids_boot` восстанавливает незавершённый секторный журнал;
он не заменён и не ускорен. Восстановление после реального обрыва может занять
больше времени, чем чистый старт. До успешного восстановления действует прежний
запрет доступа к непубликованной базе.

## Замер

`Tests/measure_user_init.py` до/после исполняет связанные функции IAR и добавляет
измеренную стоимость W25/SPI. Фикстура прежняя: 3151 ID, 127 событий, 3 временных
ID, готовые расписания, NOR не BUSY. Оба профиля дают одинаковые числа.

| После `user_comm_boot` | До | После |
|---|---:|---:|
| Чтения основного ID-прохода при инициализации | 6257 / 1 601 600 Б | 0 / 0 Б |
| Сам проход / его запуск, мс | 1779,657–4054,073 | 0,000–0,001 |
| Сумма прежних измеряемых шагов, мс | **1786,879–4071,080** | **7,222–17,008** |
| Обычный квант восьми живых ID, мс | — | около 0,262–0,601 |
| Последний квант с полностью занятым сектором отметок | — | не более 4352 Б; около 4,97–11,48 мс |

Отдельная фикстура первой карты: один ID в ячейке 50048, группа 1, остальные ID FF.
Первый полный путь Wiegand для этого ID заканчивается оценочно через
1,595–3,664 с от начала измеряемой части инициализации: база читается один раз,
дальше ID дважды сверяется отдельными чтениями 32 Б. Выход и событие 71 проверены
на модели. Чистый POR с действительным `user_ids_boot`: первый запрос `AT` на
5000 мс, обычный сброс — на 7000 мс. Статус 101 при незавершённом проходе не уходит.

Это оценки инструкций и модели SPI, не время физической платы. Начальные
`mem_recover`/настройки перед `user_comm_boot`, физический BUSY и конкурирующие
длинные линейные поиски здесь не включены. Произвольная нагрузка картами и
восстановление журнала могут задерживать обслуживание AT; обещания строго 5000 мс
при любой такой нагрузке нет.

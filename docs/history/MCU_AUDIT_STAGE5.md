## Журнал и восстановление

Схема адресов и проверка инструментов/образов: [MCU_AUDIT_STAGE5_PLAN.md](MCU_AUDIT_STAGE5_PLAN.md), коммит `eda1c98`, после которого владелец разрешил продолжение.

| Внешняя flash | Назначение | Размер |
|---|---|---|
| `0x1F5000..0x1F8FFF` | Прежние два config slot: data + metadata | Без изменений |
| `0x1F9000..0x1F9FFF` | Новый scratch: полный новый образ сектора | 4096 байт |
| `0x1FA000..0x1FAFFF` | Новые metadata: адрес, длина, CRC32, commit | 4096 байт |
| `0x1FB000..0x1FFFFF` | Остаток до границы 2 МБ | Не используется журналом |
| От `0x200000` | Фото при соответствующем профиле | Без изменений |

`storage` проверяет резервирование обоих секторов по действующим mem[]/config/boot границам. Все физические сектора до 3 МБ сверяются с независимым ожидаемым перечнем допустимых destination. Публичные mem_write/mem_erase_* отвергают попытки записи в scratch/metadata; boot_ext_* сохраняют прежнюю область до `0x40FFF`. В плане проверены 118 отдельных образов и 16 образов из 11 ZIP, исходники инструментов и варианты старых карт. Полного дампа внешней flash с платы нет; размер бинарника сам по себе не доказывает карту данных старой прошивки.

Порядок: восстановить предыдущую транзакцию → стереть metadata и проверить пустоту → стереть scratch → записать его 16 страницами по 256 → проверить CRC32 и весь образ → записать/проверить первые 28 байт metadata → последним записать commit → восстановить destination → проверить CRC32 и полное совпадение → стереть/проверить metadata. Watchdog обслуживается между страницами и блоками проверки. Readback-ошибка отдельно от несовпадения данных прекращает операцию.

`mem_rewrite` и все восемь сбросов секторных буферов в командах 13–16 используют журнал. Recovery выполняется перед чтением таблиц при старте; после отказа отдельные области конфигурации/связи остаются доступны, а таблицы и локальные проверки доступа защищены. Проверка длин аргументов предшествует проверке готовности памяти: повреждённый кадр по-прежнему получает PARAMERROR без выделений и записи. Ошибка сохранения не обновляет timestamp.

Незавершённые или разорванные metadata без действительного commit не разрешают стирание destination. Если действительный commit есть, но scratch не проходит CRC/readback, журнал сохраняется, таблицы блокируются; автоматического стирания единственной подтверждённой копии нет. Восстановление повторяемо, в том числе при повторном обрыве и при разорванной окончательной очистке metadata.

Атомарность относится к одному сектору. Команда на несколько секторов при отказе может оставить уже завершённый новый префикс и старый остаток; timestamp успешной команды не подтверждается. Полная атомарность многосекторной команды в этот этап не входила.

## Изменения загрузчика 0x32

Минимальные изменения перечислены отдельно:

1. `DomovoiBoot.ewp` подключает общее `User/sector_journal.c`, то же ядро подключено в `DomovoiNext.ewp`.
2. В `boot_platform.c` существующие операции SPI выделены в закрытые storage_read/erase/write. Публичные boot_read/boot_ext_* сохраняют прежние границы; общий журнал получает отдельные ограниченные callbacks.
3. `boot_start_app` вызывает sj_recover до проверки/передачи управления приложению. Это покрывает старт текущей программы и запуск старой после отката. При отказе возврат оставляет существующую обработку USB загрузчика доступной.
4. `sj_io_service` использует существующий boot_service для watchdog/USB. boot_main.c, boot_core.c, процедура замены по команде 110, footer/version `0x32` не менялись. Оба собранных BIN остаются 32768 байт.

**Установленный прежний загрузчик 0x32 этого восстановления не содержит.** Защита при откате на старое приложение требует отдельной установки нового загрузчика владельцем; совпадение номера версии не означает наличие recovery. На платы ничего не записывалось. Текущая новая прошивка умеет восстановление сама.

# USB-диагностика связи — 2026-10-11

База `552d21a`, ветка `task/link-diag`. Оценка до изменения кода: ReleaseCustomer (DIAG=0) +80–88 байт ОЗУ, +600–1000 байт Flash; для Release (фактически DIAG=1) ожидается перенос существующих данных и изменение размера USB-ответов. В текущем EWP Release не переопределяет DOMOVOI_DIAG, поэтому получает 1 из user/domovoi_diag.h; ReleaseCustomer задаёт 0. Конфигурации не меняются.

Согласовано: шесть этапов — питание, настройка, SIM, сеть, PDP, TCP. 30 внутренних шагов остаются только под DIAG. Для точного времени этапов в мс нужны 6×4=24 байта, для десяти упакованных сбоев 10×4=40 байт; к этим 64 байтам добавляются начало этапа/попытки, индексы, маска завершения и данные оператора. Насыщение 16-битных миллисекунд не подходит: PDP/TCP допускают 150000 мс.

До кода изучен [статический кольцевой буфер Zephyr](https://docs.zephyrproject.org/latest/kernel/data_structures/ringq.html). Используется имеющееся кольцо с фиксированной вместимостью, сторонний код и библиотека не добавляются.

## Реализация

- `User/c/user_commands.c`, `User/c/user_diag.c`: USB 112 без PIN при DIAG=0/1, один кадр 93 байта, версия 3; общий сборщик не содержит внутренних счётчиков.
- `Modules/modem_slm336.h`, `Modules/comm_modem.c`: шесть uint32 времён, начала этапа/попытки, completed_phases и кольцо 10 uint32 постоянно; одни поля для обеих сборок. Старые массивы failure_step/reason/seconds и старый сборщик 112 удалены. Сбои сервера записываются без изменения рабочего шага модема.
- `Modules/comm_channel.c/.h`: последний результат уже существующего ping/DNS ya.ru, сохраняющийся между переподключениями.
- `Modules/comm_info.c/.h`: PLMN из существующего QNWINFO, без дополнительного опроса.
- `Modules/comm_recover.c/.h`, `Modules/comm_server.c/.h`: код причины по рабочим состояниям; два бита в существующем байте флагов сервера сохраняют исход отказа регистрации/проверки, отдельного автомата нет.
- `User/prof.c/.h`: отладочные поля UART/автоматов перенесены в 111 v6; 113 отправляется вместе с 111. DIAG=0 не содержит этих команд/счётчиков. 30 времён AT, completed_steps, last_code/APN остаются DIAG.
- Тесты: `Tests/test_link_diag.c`, существующие `test_comm_slm.c`, `test_comm_channel.c`, `test_comm_server.c`, `comm_server_host.py`, `comm_mutations.py`, `run_all.py`, `asm/test_diagnostics_config.py`, `asm/test_stage4_usb.py`.

Полный формат и фразы для монтажника: `docs/protocol/usb_link_diag.md`. Кратко: SLDN / length85 / адрес0 / UID / 112 / v3 / код / GSM / CSQ / сеть / ya.ru / PLMN7 / ожидание32 / 6×время32 / число сбоев / 10×упакованный сбой32 / CRC16. Серверные кадры, загрузчик и адреса 0x08008000/0x08008200 не изменены.

Есть CSQ, укрупнённая технология и числовой PLMN; текстового имени оператора нет. Сведения появляются после существующего фонового опроса, при неготовом модеме помечаются неизвестными. Ping/DNS — последняя существующая проверка, USB новую не инициирует.

## Размеры по MAP

Flash = readonly code + readonly data; ОЗУ = readwrite code + readwrite data (включая существующие стеки/резервы). IAR EWARM 9.2, исходная база 552d21a; до — `%TEMP%/domovoi-agent-build/link-diag-before`, после — `%TEMP%/domovoi-agent-build/link-diag-after`.

| Сборка | Flash до | Flash после | Прирост | ОЗУ до | ОЗУ после | Прирост |
|---|---:|---:|---:|---:|---:|---:|
| Release (DIAG=1) | 79695 | 80111 | 416 | 17261 | 17282 | 21 |
| ReleaseCustomer (DIAG=0) | 77252 | 78152 | 900 | 16875 | 16960 | 85 |

До: Release ro code75419/data4276, rw code516/data16745; ReleaseCustomer ro code72979/data4273, rw code516/data16359. После: Release ro code75835/data4276, rw code516/data16766; ReleaseCustomer ro code73879/data4273, rw code516/data16444.

Оценка до кода +80–88 ОЗУ/+600–1000 Flash подтверждена для рабочей сборки без DIAG. Ориентир 64/600 превышен на 21/300 байт: только точные времена и история требуют 64 байта; ещё нужны две временные отметки, индексы, признак завершённых этапов и PLMN. По модулям ОЗУ: modem +76, info +8 с выравниванием, channel +1; server/recover без прироста. Прирост ro code по MAP: user_diag +224, user_commands +28, modem +220, recover +136, server +138, channel +36, info +120 байт; итог по всем модулям +900 с учётом компоновки. Это сборка кадра/CRC через существующий packet_send, обновление времён/кольца, выбор причины и извлечение PLMN. Уменьшение длительностей до uint16 ограничило бы этап 65535 мс при штатном таймауте PDP/TCP 150000 мс; сокращение истории или отказ от PLMN нарушили бы требование. Новых автоматов, AT-опросов, динамической памяти и дублирования общих полей нет.

## Проверки и ограничения

Модель связи: восемь кодов (семь причин/состояний и «подключение»), точные шесть времён и их остановка, ожидание с истёкшим сроком, ping/DNS/нет ответа, PLMN с ведущими нулями и неверным полем, кольцо через переполнение и перезапуск, секунды более 65535, побайтный 93-байтный кадр с независимым CRC. ELF обеих сборок: наличие 112 без PIN, USB-only, точный пустой кадр, отсутствие отладочных команд при DIAG=0, 111+113 при DIAG=1. Добавлено 12 мутаций: восемь кодов, граница/вместимость/порядок/секунды кольца.

Итоги MAP полного прогона совпадают с таблицей. Исходный и итоговый MAP имеют одинаковое предупреждение Ls016 о непрямых вызовах при статическом анализе стека; новых предупреждений/ошибок нет. Проверка мёртвого кода PASS; записей для удалённого формата 112 в `Tests/dead_code_allowlist.json` нет, allowlist не менялся. Проверки выполняются на модели и IAR ELF; физическая плата, операторская сеть, USB-драйвер NextConfig и живой сервер не проверялись. Коммитов и прошивки нет. Вопрос для интеграции NextConfig: показывать числовой PLMN или добавить собственный справочник названий операторов. Текущее значение Release DIAG=1 сохранено, как в исходном EWP; исправлять конфигурацию сборок эта задача не требует.

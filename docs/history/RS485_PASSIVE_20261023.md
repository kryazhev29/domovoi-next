# Пассивный режим RS-485: номер с линии открывает ворота

**Дата**: 23 октября 2026 г.
**Ветка**: `task/rs485-passive` от `task/flash-reserve` (7bc4704).
**Среда**: облако без IAR, zig и платы; host-стенды собраны gcc 13 через обёртку вместо zig cc.
**Не трогалось**: сервер, NextConfig, загрузчик, форматы протокола и внешней флеш, плата.

## Что сделано

1. **Один хозяин линии 485** — `rs485_init()` (`User/c/photo_runtime.c`). Порядок: выбран Wi-Fi-модем
   (`device.wifiModem`) или мост ещё выключается (`comm_channel_wifi()`) — порт у моста, буфера у приложения нет;
   идёт снимок — буфер камеры назначает сама камера (`PR_CAMERA`); иначе при `rs485Mode == 0` линия слушается
   в буфер `wf_line`; при `rs485Mode == 1` без опроса устройств буфера нет (байты отбрасывает драйвер).
   Переходы — все через `rs485_init()`: старт (`user_init`), конец снимка (`photo_stop`), команда 12
   (`rs485_set_config`), выбор модема (USB 114, `user_store.c`), снятие выбора модема и долг выключения
   `wifiStop` — после последнего `off` невыбранного моста (хвост `wifi_done` в `Modules/comm_wifi.inc`:
   `if (comm_channel_wifi()) wifi_rebuffer(); else rs485_init();`). Новых состояний и флагов нет: хозяин
   выводится из `device.wifiModem`, `comm_channel_wifi()`, `device.getPhoto`/`photo->stage` и `config.rs485Mode`.
2. **Пассивный режим** — `rs485_readedID()` (`User/c/user_access.c`), вызывается из `port_check_data()`
   (`User/c/user_main.c`) после паузы приёма 10 мс (`uart_setRecTimeout(10)` в `rs485_init`; `photo_stop`
   теперь тоже возвращает 10 мс после 2 мс драйвера камеры). Посылка -> ID -> захват команды 6 с источником 3
   (событие 78 + ответ 8, как у Wiegand) или `user_checkIdAndControl(id, CT_OTHER)` — разрешение реле
   «от 485 прочие». Общая часть с Wiegand вынесена в `reader_id()`; `WG_readedID` стал её вызовом.
3. **Путь RFID в доступе**: `CT_RFID` -> реле `onRFID` (было `onOther`), группа `onRFID` (не проверялась),
   событие 70 `LOG_CON_OUTONBYRFID` (не писалось). `CT_OTHER` -> событие 70 (см. решения).
4. **Активный опрос не делался**; место для него описано ниже.

Изменённые файлы прошивки: `Modules/comm_channel.h`, `Modules/comm_wifi.inc`, `User/c/photo_runtime.c`,
`User/c/user_access.c`, `User/c/user_logic_internal.h`, `User/c/user_main.c`.
Тесты: новые `Tests/test_rs485_id.c`, `Tests/test_rs485_owner.c` (группы `rs485id`, `rs485owner` в
`run_host.py`/`run_all.py`, внесены в `check_comm_sources.py`); `Tests/test_comm_channel.c` — заглушка
`rs485_init` и проверки возврата линии; `Tests/asm/test_fixes1_mutations.py` — два якоря D09 переведены на
`reader_id` (поведение мутантов прежнее).

## Решения

- **Буфер приёма — `wf_line[96]`, строка моста** (`comm_wifi.inc`, теперь внешняя, объявлена в
  `comm_channel.h`). Проверено по коду, что вне моста она свободна: все обращения к ней — в `wifi_keep`,
  `wifi_unhold` и через `wf.buffer`, то есть внутри `wifi_*`, которые `comm_channel_poll` вызывает только при
  `comm_channel_wifi() != 0`; `comm_channel_wifi_setup`/`comm_channel_wifi_scan` при `wf.mode == 0` возвращают
  до обращения к буферу; `comm_channel_wifi_info` читает `wf_ssid`, не `wf_line`. Слушатель получает буфер
  только при `!device.wifiModem && !comm_channel_wifi()`, а разбирает — при `!comm_channel_wifi()`; повтор
  выключения по долгу `wifiStop` сначала делает `comm_channel_wifi() != 0` (`wf.f.stop`), затем забирает буфер
  `uart_rebuffer`'ом и после `off` отдаёт его обратно `rs485_init`. Нового ОЗУ нет; главный цикл и ISR не
  пересекаются по буферу иначе, чем у моста и камеры (`uart_clear` после разбора).
- **Разбор посылки**: ID — последние 10 печатных ASCII (0x21..0x7E). CR, LF, пробел и прочие управляющие
  (< 0x21, 0x7F) — разделители и пропускаются. Байт ≥ 0x80 — мусор: посылка отбрасывается целиком без записи
  (шум линии не превращается в «ID не в базе» и SMS администратору). Полный буфер (96 Б) — слишком длинная
  посылка: драйвер уже отбросил байты за границей, хвост (а это и есть ID) мог пропасть — отбрасывается.
  Две посылки в одном кадре (доступ ждал флеш) — берётся последняя. Пустая посылка (только разделители) — ничего.
- **Короче 10 — нули слева, как у Wiegand** (`format_id`: `00` + 8 hex). База сравнивает ровно 10 символов;
  захват командой 6 и доступ идут одной и той же нормализацией — что админ захватил, то и откроет.
  Выравнивание вправо с нулями совпадает с Wiegand и с числовой записью номера («12345678» -> «0012345678»),
  поэтому базы, собранные с Wiegand-считывателя и с 485-считывателя одного номера, совместимы.
  Регистр не меняется, буквы и знаки принимаются как есть (считыватели шлют hex в обоих регистрах).
- **Очередь без ОЗУ**: если доступ не готов (`user_access_ready`: идёт поиск ID, занят исполнитель при нужной
  записи счётчика) — кадр остаётся в буфере UART до следующего прохода, как 4-кадровая очередь Wiegand, но без
  памяти; подошедшая следом посылка допишется в тот же кадр и перекроет первую (берутся последние 10).
- **Захват (команда 6)**: источник 3 — ответ 8 и событие 78, захват снимается; `addressGetID` в пассивном режиме
  не используется (он для адресного опроса). Во время чужого захвата (Wiegand) посылка 485 не даёт доступа и
  захват не снимает — симметрично D09 для Wiegand. Мусор при захвате захват не снимает (таймаут сервера остаётся).
  Проверка команды 6 (`ptr[6] == 3 && ptr[7]`, адрес ≠ 0) не менялась.
- **`CT_OTHER` при проходе — событие 70 «Управление выходом по ID RFID 485»** (`docs/protocol/event_log.md`,
  строка 58). Своего события у «485 прочие» в листе нет; по `controller_functions.md` (строка 72) RFID — «только
  считыватели, подключенные через RS485», пассивная линия — это и есть такой считыватель; 73 — автономер/камера.
  Без события проход по 485 не попадал бы в журнал сервера. Разрешение группы для `CT_OTHER` не проверяется:
  у группы нет флага «прочие» (Протокол2, строки 345–349) — как и было.
- **Скорость**: `rs485_baud()` прежний; при выбранном модеме или выключающемся мосте — 115200, иначе
  `config.reserv[0]`. После последнего `off` снятого моста скорость и буфер возвращаются к настройке 485
  (раньше порт оставался на 115200 со строкой моста до следующей команды 12 или перезапуска).

## Куда встанет активный опрос

- `port_check_data()` (`user_main.c`): ветка `rs485Mode == 1` вместо простого `uart_clear()` — здесь
  обрабатывается ответ устройства после паузы приёма; очередь адресов и таймаут ответа — на месте
  `rs485_readedID`. Буфер тот же `wf_line` (назначит `rs485_init`: `listen` станет «пассивный или активный
  без камеры»), хозяин линии не меняется.
- Типы периферии `config.rs485Periphery[i].type` -> `CT_RFID` (6–12) / `CT_AUTO` (2) через ту же `reader_id`
  с источником 3 и проверкой `device.addressGetID` при захвате; `device.peripheryState[i]` для статуса 2.
- Съёмка камеры и мост остаются хозяевами выше опроса; `SLM_CFG_RS485_BUSY` для моста уже есть.

## Бюджет

Прямой замер IAR невозможен в облаке; изменённые функции до (7bc4704) и после собраны clang 18
`--target=thumbv7m-none-eabi -Oz` (скрипт в отчёте не хранится, метод повторяем: те же функции со
структурами `structures.h` и внешними заглушками):

| Функция | До | После | Δ |
|---|---|---|---|
| `WG_readedID` | 80 | 28 | −52 |
| `reader_id` (новая, общая с Wiegand) | — | 72 | +72 |
| `rs485_readedID` (новая) | — | 112 | +112 |
| `user_checkIdAndControl` (2 `case`) | 480 | 500 | +20 |
| `user_activateOut` | 436 | 448 | +12 |
| `user_access_complete` (1 `case`) | 272 | 276 | +4 |
| `rs485_init` | 64 | 108 | +44 |
| `photo_stop` | 44 | 32 | −12 |
| `port_check_data` | 56 | 88 | +32 |
| хвост `wifi_done` (встроен в `comm_channel_poll`) | 4 | 26 | +22 |
| **Итого** | | | **≈ +250 Б** при лимите 1 536 Б |

IAR `-Ohz` обычно даёт величину того же порядка (±20 %); точную — по MAP локальной сборки.
ОЗУ статическое: **+0 Б** (лимит 64 Б) — буфер `wf_line` уже существовал, новых переменных нет.
Стек: `rs485_readedID` — 11 Б локальных + вызов `reader_id` -> `user_checkIdAndControl`, та же цепочка, что
`WG_process -> WG_readedID`, но из `port_check_data` напрямую (короче на кадр `WG_process`).

## Проверить на плате

1. Пассивный режим, считыватель на 485 (9600/115200 по настройке): карта из базы открывает реле с «от 485
   прочие», событие 70 в журнале с ID из последних 10 символов; карта не из базы — событие 65 и SMS (если
   включено); длинный мусор и строка без печатных символов — ничего в журнале.
2. Захват командой 6, источник 3, любой адрес: ответ 8 с ID и событие 78; по таймауту — ответ 8 с 255.
   Во время захвата карта не открывает. Захват с источником 1 не снимается посылкой 485.
3. Команда 12: смена скорости/режима во время снимка прерывает снимок, после неё линия слушается заново;
   смена `rs485Mode` 0 -> 1 прекращает приём, 1 -> 0 — возобновляет.
4. Модем: выбор по USB 114 отключает приём (115200 мосту); снятие выбора — после `off` моста порт возвращается
   на скорость настройки и приём ID работает; с долгом `wifiStop` (мост молчал) — после повтора при старте
   модема линия возвращается приложению, журнал 41 как прежде.
5. Камера типа 3 в активном режиме на той же линии: снимок после прохода и команда 7 как прежде; после
   снимка пауза приёма 10 мс (а не 2 мс).
6. Wiegand: карта и захват (источник 1) без изменений; событие 71.

## Замечания вне задания

- `user_addIdToTempBuffer` ставит тип ячейки только для `CT_PHONE`/`CT_AUTO`/`CT_WIEGAND`: авторегистрация по
  485 (`CT_OTHER`, и будущий `CT_RFID`) пишет ID без флага `isRFID` — решение владельца при активном режиме.
- Команда 6 для источника 3 требует адрес ≠ 0 (проверка `command_args_valid`); в пассивном режиме адрес
  игнорируется. Если админка шлёт 0 — сервер получит 1 (неверные параметры); формат не менялся.
- `user_init` зовёт `uart_setRecTimeout(10)` сразу после `rs485_init`, который делает то же — оставлено.

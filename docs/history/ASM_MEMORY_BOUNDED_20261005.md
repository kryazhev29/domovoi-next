## Исполняемые изменения

Новые условия, циклы, состояния, ошибки и передача владения написаны вручную
в production `.s` для IAR Thumb-2/Cortex-M3. Повторного экспорта C для этих
изменений не было. Прежняя инвентаризация 368 экспортированных функций относится
к предыдущему этапу и не является числом новых ручных оптимизаций.

| Путь | Новая работа одного прохода | Владение и завершение |
|---|---|---|
| Перестроение индекса | Один ограниченный шаг чтения/сканирования либо async W25 start/poll | Долговечная инвалидная метка до стирания, 64 сектора, verified перед конечной валидной меткой; стабильный источник записи |
| CRC команд 17/18 и ответ config | CRC раздела до 64 байт; один GF(2)-шаг FF; конечная CRC ответа до 205 байт | Собственный снимок и ответ; ошибки чтения не превращаются в успешную CRC; retry занятого транспорта |
| Журналы/временные ID, команды 9/10 | Одна запись до 32 байт либо CRC до 64 байт | Context и пакет зарезервированы до ACK/изменения курсора; durable config; TX lease не выходит за один проход |
| Истечение срока ID | Сканирование по 64 байта, отдельные шаги поиска и секторного журнала | Снимок исторического блока 1024 байта сохраняет поведение дубликатов; событие 138 только после verified |
| USB cmd103 | Один start/poll стирания | Все границы/выделение проверены до стирания; счётчики и ACK103 после всего проверенного раздела |
| FW cmd19/rollback | CRC/копирование образа по 64 байта, async стирание/запись | Резерв будущего config snapshot до разрушительных операций; verified config и собственный ACK до запроса/копирования |
| Ответы новых владельцев и фото | Неблокирующая постановка целого пакета в USB ring | PRIMASK сохранён; данные до единственной публикации указателя; epoch/configuration проверены под маской IRQ |

Основные новые модули: `User/asm/service_runtime.s`, `upload_runtime.s`,
`expiry_runtime.s`, `idclear_runtime.s`, `fw_service_runtime.s`.
Перестроение индекса находится в `idindex_runtime.s`, USB writer —
`usb_stm32f10x_runtime.s`. Связки владельцев, reset, reconnect и основного
планировщика находятся в `user_fun_runtime.s` и `memory_runtime.s`.

Pending, отказ I/O и verified различаются. Вызванная отмена не освобождает
источник незавершённой async-записи. Reset дренирует начатую операцию;
смена сеанса подавляет устаревший ответ. Новые автоматы продолжаются через
`user_storage_poll`, без новых входящих данных. Каналы, номера команд,
форматы пакетов, адреса и форматы Flash сохранены.

## Память

* `cfg_job`: 104 → 40 байт. Его page64 использует `sjr.data` только после
  освобождения прежнего владельца. Config, таблицы и фото исключают
  пересечение; дополнительные служебные владельцы закрывают прямой begin.
* `sjr`: 192 → 128 байт. Синхронная проверка check64 живёт в стеке вызова,
  async W25 использует постоянные данные/заголовок. Это экономит ещё 64 байта
  RAM ценой 64 байт стека соответствующего journal poll.
* Короткий runtime `cfg_read` использует проверенный startup cache; он больше
  не пересчитывает обе 4-КиБ копии конфигурации при каждом чтении.
  Для 64 байт: 72460 → 46 инструкций, NOR 8288 → 64 байта, стек 184 → 24.
  Startup validation сохранена; cache обновляется после verified commit.
* Heap и CSTACK остаются по 4096 байт. Очереди, максимальные пакеты и разделы
  не уменьшались. UART/DMA и USB rings сохраняют отдельную постоянную память.

Исходные **3808/4096** воспроизведены как стрессовое одновременное выделение
chunks `[192,1048,544,2024]`, а не доказанная допустимая цепочка подсистем.
Фото TX 544 исключает приём таблицы/выгрузки и config snapshot; USB driver
вообще не выделяет этот предполагаемый heap 1040 — его кольца статические.
Поэтому сопоставление «3808 → 2320 экономии heap» было бы неверным.

Реальная камера создаёт photo state 192, затем при разрешённой выгрузке с ACK
наблюдаются chunks `[192,48,1048,1032]`: 2320 занято, 1776 свободно,
крупнейшее допустимое выделение 1768, внешняя фрагментация 0. После ACK и
ответа остаётся photo 192. При таблице 63 строк допустимый пик 2216, при FW с
резервом config — 1360. Это проверенные цепочки, не доказанный глобальный пик.

Отдельный стресс фрагментации: свободно 1296, крупнейший chunk 776/payload 768,
фрагментация 40,123%; после освобождения всё сливается в chunk 4096/payload 4088.
OOM/отсутствие достаточно большого непрерывного блока проверяются до
инвалидирования, стирания или подтверждения курсора. FW резерв 1024 передаётся
config через `free → store_snapshot → mem_config_begin → malloc1024` без
промежуточного выделения; проверен тот же адрес блока.

## Существенные ограничения

* `reader_id → user_checkIdAndControl → user_findID`: fallback по всей базе
  остаётся синхронным; в проверенной сцене 896288 инструкций и 1601536 байт
  чтения. Индексированный поиск тоже остаётся ограниченным синхронным API.
* `user_activateOut → user_updateID → mem_patch`: сохраняется синхронный
  journal; в сцене 394331 инструкций,65666 байт чтения,4 erase и 34 program.
  Эти цепочки не выполнялись на устройстве и реле не вызывались.
* Factory reset из cmd3/таймера/регистрации/SMS сохраняет синхронные очистки,
  сохранение default config и повторную инициализацию. Здесь выполнен аудит
  исходников, не модельное исполнение команды сброса.
* Startup/recovery, отдельные старые служебные API, задержки reset/manual
  boot и void-ответы через старый USB helper остаются синхронными. Новая
  `usb_try_send` применяется к владельцам, которые умеют сохранить ответ и
  повторить его; глобальная замена всех отправок не производилась.
* Массовая очистка ID неатомарна, как прежде: после обрыва может сохраниться
  часть раздела. Незавершённая операция не получает успешный ACK.
  Прерванный rollback требует повторения cmd19; новый persistent формат
  намеренно не вводился, текущий внутренний образ не заменяется частичным.
* IAR Ls016 и непрямые вызовы ограничивают статический анализ стека.
  Его число 2360 также включает сохранённые недостижимые исторические тела;
  таблица roots не содержит включённых Wiegand EXTI2/3. Вложенные IRQ
  возможны. Измеренные отдельные цепочки и IRQ-вставки не являются
  доказательством глобального максимума CSTACK.

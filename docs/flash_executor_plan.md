# Один исполнитель внешней флеш — этап 1

Дата: 07.10.2026. Проверяемая база: `5fe9af1`, плата v5 HW139 / STM32F103CB / SLM336. Прочитаны `AGENTS.md`, `PROJECT_STATUS.md`, `docs/decisions.md`. Код и протоколы на этом этапе не менялись; платы, сервера и коммита нет. Артефакты проверки: `%TEMP%\domovoi-flash-build`.

**Итог описи: 43 группы обращений в работе, 9 дефектов, 1 уже закрытый дефект установки FW.** Группа объединяет одну цепочку вызовов или один автомат; перечисленные внутри строки вызовы не являются ещё одной группой. Стартовые обращения вынесены отдельно. Условные отказы API при обходе внешней защиты не включены в число 9.

**Этап 2: E01–E09 исправлены точечно** на базе `593f01d`; E05 — в согласованном
минимальном объёме «не терять запрос при занятой флеш», без общего результата
заводского сброса. [Исправления, размеры, ELF-тесты и мутации](history/FLASH_FIXES_20261007.md).
Полный исполнитель, очередь восьми запросов и вытеснение сейчас не реализуются.
Следующий отдельный этап — одна структура работы и один switch вместо 12 `*_active()`.
Разделы ниже сохраняют исходный аудит и предложения этапа 1; E01–E09 в них —
историческое состояние до исправлений, а не оставшаяся задача будущего исполнителя.

## 1. Что сейчас считается занятостью

| Состояние | Поведение и граница |

Коды в `User/asm/flash_owner.h`: ID-clear `81`, expiry `82`, FW-service `83`, upload `84`, index `85`, CRC `86`, table `87`, photo `08`, FW-block `09`, log `0A`. Это **10 кодов + настройки + служебная работа store = 12 типов**, а не 12 независимых физических устройств. CRC сервиса и фоновый CRC делят код `86`; ACK журнала пользуется автоматом настроек.

Текущая цепочка `user_storage_poll` (`User/c/user_store.c:172–188`): CRC ответа → ACK журнала → фоновый CRC ID → index → expiry → upload → ID-clear → FW-service → table → photo → FW-block → log → config; затем reply/recovery/erase, журнал RAM, reset/save (`:189–285`). Это порядок проверки уже активных состояний, **не вытесняющая очередь**. Index дополнительно запускается из `user_loop:107`; фото — из `photo_poll`.

## 2. Опись в работе (`store_runtime=1`)

В таблице файлы без каталога находятся в `User/c/`; пути `User/...` и `Bootloader/...` указаны полностью. Ч/З/С — чтение/запись/стирание. «Авт.» — автомат, исполняемый главным циклом. Для автоматов «чужой BUSY» означает нарушение текущей внешней сериализации: обычное ожидание **своей** команды не является отказом. Адреса строк относятся к базе выше.

## 4. Предлагаемый исполнитель

**Выбор: все runtime-чтения и изменения исполняет один модуль.** Карта, звонок, SMS, команды и сцены ставят запрос; обработчик не ждёт в цикле. Для уже свободной флеш исполнитель может исполнить короткий запрос сразу в том же проходе, но W25 вызывает он сам. Самостоятельные «разрешения на чтение» внешнему коду не нужны.

### Состояние, очередь и приоритеты

| Элемент | Конкретный контракт |
|---|---|
| Одна текущая работа | `kind`, `step`, `result`, `request_id`, источник/epoch, диапазон блокировки, адрес/прогресс, указатель на удержанные данные, union параметров работы. Все варианты обслуживает один switch по kind; активность = kind≠NONE. Никакой цепочки из 12 active-функций. |
| Физическая команда | Существующий `w25_job` остаётся низкоуровневым дескриптором команды/проверки, **не вторым владельцем**. CRC-дельта — параметр записи ID, не отдельный конкурент; убрать её присвоения в чужой `w25_job`, алгоритм CRC оставить. |
| Приём | ACCEPTED + token; затем PENDING → OK / IO_ERROR / INVALID / CANCELLED. Занятость принятого запроса остаётся PENDING, не увеличивает ошибки FW и не пишет 133. Источник кадра сразу копируется/удерживается до освобождения; channel/uniq/epoch входят в запрос. |
| Очередь | 8 фиксированных дескрипторов по ориентиру 24–32 Б, из них 4 резервируются для доступа. Отдельные постоянные mailboxes confirm/rollback/reset: их нельзя потерять из-за заполнения общей очереди. Save одного поколения объединять; каждый ответ команды связан с token. Нет кучи и копий всей базы. |
| Переполнение | Непринятый серверный/USB-запрос остаётся во входном буфере с backpressure; Wiegand снимает завершённые кадры в 4 отдельных слота независимо от флеш. Предельный пятый кадр требует наблюдаемого счётчика переполнения и определённого отказа входа, не IO_ERROR. Конечная RAM не гарантирует сохранение бесконечного потока. |
| Приоритет 0 | Завершить уже запущенную аппаратную команду; не бросить committed-сектор. Confirm/rollback обслужить в ближайшее безопасное окно прежде нового длинного шага. Confirm — единичная запись 4 Б, потому ставится перед картой и имеет жёсткую связь с таймером пробы. |
| Приоритет 1 | Карта у двери, звонок, команда 8: прочитать согласованные данные; если надо, сохранить счётчик/первый проход и только затем включить реле. Для равных запросов FIFO. |
| Приоритет 2 | Принятые команды/ответ серверу и USB, настройки, пакеты загрузки FW, чтение/ACK выгрузки. Передача готового ответа освобождает флеш: ждать транспорт должен транспортный контекст, а не текущий flash-job. |
| Приоритет 3 | Журнал. При ≥12 из 16 событий повышать до уровня 1 между законченными запросами доступа; резервировать место/удерживать критические события FW/загрузчика до долговечной записи. Остальным источникам вернуть явное непринятие, не обещать бесконечную ёмкость. |
| Приоритет 4 | Фон: индекс/CRC, expiry, сканирование фото и очистки. Квота: при отсутствии deadline после 8 завершённых запросов более высокого уровня выполнить один безопасный фоновый шаг. Объёмный accepted-запрос хранит прогресс и получает ограниченные кванты, а не весь цикл до конца. |

После BUSY исполнитель сначала допускает срочное чтение **другого согласованного диапазона**, затем продолжает 64-Б проверку собственной записи. Буфер незавершённой W25-команды не переиспользуется. Вытеснение — приостановить текущий контекст, вернуть его в очередь, исполнить срочный запрос и возобновить; одновременно активен один kind. Один приостановленный изменяющий контекст удерживает свои данные/журнал; другие писатели ждут. Небольшой отдельный буфер доступа не пересекается с `sjr.data`/FW/config/USB.

В начальном варианте кадры большого размера по-прежнему допускаются **по одному**: нынешний `work_memory` перекрывает таблицы/FW/config. Дескриптор очереди не делает эту память совместимой. Не принимать второй payload до предоставления ему устойчивого буфера; транспортный borrowed-буфер нельзя переиспользовать. Прерывания только принимают кадры, исполнитель работает главным циклом.

### Согласованность и задержка до реле

Чтение доступа — цельная логическая работа: ID → группа → расписание/праздник → возможная правка ID → реле. До её результата не изменять прочитанные таблицы. На время destructive-фазы сектор-журнала конфликтующий диапазон закрыт; независимые boot-journal/log/FW/таблицы не закрываются одним глобальным битом. Внутри одного принятого пакета расписаний читатель видит целиком старую либо новую версию. После реального committed-отказа блокировка остаётся до существующего восстановления.

| Сценарий | Сейчас | После; оценка, не замер платы |
|---|---|---|
| Свободно, индекс готов, ID без сохранения | 25 мс тишины Wiegand + текущий проход + синх. поиск | Та же тишина + ≤одного прохода исполнителя + короткие чтения. 18 МГц SPI: 64 Б с адресом ≈30 мкс чистого провода, 256 Б ≈116 мкс; CPU/IRQ сверх этого надо измерить. Цель добавочного ожидания очереди ≤5 мс при свободной флеш. |
| Запись/стирание **другого** диапазона | Ожидание всего владельца, включая CRC/сеть/ротацию; общей верхней границы нет | Остаток одного аппаратного BUSY + проход + чтение. Текущие пределы драйвера — 20 мс program, 1000 мс erase (`flash_w25_runtime.c:56`); разумная верхняя расчётная граница около 25/1005 мс при проходе ≤5 мс. Это предел до классификации аппаратного таймаута, не типичное время W25. Полную проверку FF 4096 Б читатель другого диапазона ждать не обязан. |
| CRC/индекс/выгрузка, сейчас без физической записи | Читателей блокирует логический владелец, иногда до отправки ответа | Фоновый read ≤64 Б за квант (CPU-бюджет ≤1 мс); срочный read в следующем проходе. Готовый пакет не держит флеш во время сетевого ожидания. |
| ID без готового индекса, полный перебор | До 1 601 536 Б синх. чтения: один SPI-провод ≥0,71 с, CPU больше | Порционный запрос с тем же худшим объёмом: общего обещания «карта за 5 мс» нет. Пересборку индекса вести в фоне; fallback не подменять отказом доступа. |
| Нужно сохранить проход/первое использование ID | До реле синх. сектор-журнал: 4 стирания + копия 4096 Б дважды + метки; цикл заблокирован | Тот же долговечный порядок, но асинхронно. По нынешним таймаутам и 64-Б шагам грубый потолок 4×1000 + 130×20 ≈6,6 с плюс проверки/проходы/CRC-дельта. Для синх. 256-Б копирования число program-команд меньше; точное сравнение только моделью времени и платой. Принцип «счётчик сохранён до реле» не ослаблять ради скорости. |
| Карта в изменяемом секторе/таблице | Вся работа владельца до CRC/ответа; два кадра могут потеряться | Ждёт безопасной публикации конфликтующей транзакции; эта работа получает приоритет доступа до commit/проверки. Не читать стёртые/полузаписанные данные. При bulk-clear целой базы доступ может законно ждать/отказывать по состоянию базы: это не BUSY-ошибка чтения. |

Одновременно ждать завершения независимой записи и читать W25 невозможно. Без suspend-команд/второй флеш нельзя гарантировать миллисекундный отклик во время физического sector erase; эти изменения здесь не предлагаются. Формулы требуют измеренного максимального времени прохода главного цикла; текущие ELF-модели считают инструкции/шаги, а не реальное время NOR.

### Обязательные работы и результат

| Работа | Последовательность у исполнителя |
|---|---|
| Confirm пробы | Принятая успешная регистрация ставит устойчивый RAM-mailbox. Записать/проверить точный 0 по `BOOT_JOURNAL+28`; только тогда снять trial, отменить rollback и записать существующее событие 136 (LOG_FW_DONE). До результата не терять намерение при повторной регистрации. При настоящем отказе сообщить его отдельно; не объявлять подтверждение. По истечении 30 мин уже принятый confirm завершить прежде конкурирующего rollback; после питания без подтверждённой метки решение остаётся у загрузчика. |
| Rollback пробы | Запрос сохраняется до проверенной записи `BOOT_JOURNAL+36=0`; reset зависит от OK. Настоящий отказ не называть успешно запрошенным откатом; оставить диагностируемое состояние и ограниченную политику повторов. |
| Установка FW | После последнего блока оставить запрос, порционно проверить заголовок/векторы/CRC, стереть BOOT_JOURNAL, затем последней записать magic кандидата. Только OK → событие установки → flush/reset. Новые блоки/ручной загрузчик этого образа на это время запрещены; пустые промежутки не отменяют намерение. |
| Настройки, save/reset | Snapshot config+device поколения → прежний A/B-порядок → результат. Обработчик команды/SMS не пишет синхронно; завершение/ответ только после OK. Reset — барьер после обязательных записей и журнала. Заводской сброс — отдельная большая работа с результатом каждой очистки и существующими средствами возобновления. |
| ID доступа / temp-ID | Запрос несёт копию ID и нужную правку; читает/проверяет исходную запись, использует прежний сектор-журнал или direct append. Счётчик/first-pass и cursor публикуются после проверки; реле зависит от OK там, где сохранение обязательно. Temp-ID не теряется из-за занятости; duplicate-check отличает NOT_FOUND от IO_ERROR. |
| Отчёт загрузчика | Прочитать результат один раз, удержать событие при полной RAM, записать его долговечно, затем reported=0. При обрыве между событием и меткой возможен повтор; без нового формата нельзя обещать exactly-once. Текущая метка означает регистрацию события для выгрузки, не сетевой ACK сервера. |
| Ручной загрузчик | Stage erase/write/read/validate — запросы с настоящим результатом; убрать ложные return=1. RAM-замена — специальная эксклюзивная работа после полного drain W25, освобождения транспорта и проверенного образа. Её SPI-чтение является продолжением исполнителя при остановленном цикле, а не параллельным клиентом. Алгоритм RAM-прошивки и его существующий риск питания не расширять. |

### Что удалить и что сохранить

| Удалить/свести | Сохранить |
|---|---|
| `flash_owner` и бит 7 как общий runtime-lock, `flash_claim/release/read_allowed`; цепочку active-проверок, отдельные waiting/result флаги верхних владельцев — заменить kind/step/result | Форматы таблиц, ID и CRC, расписания 16 Б + хвост, события и wire-ответы; никакой миграции старого журнала |
| Разрозненные command/flash/background-ready проверки и дубли «занято → ошибка»; transport-admission и совместимость RAM оставить как самостоятельные проверки | Сектор-журнал и его формат/COMMIT/восстановление; A/B-слоты, поколение/CRC/заголовок-last |
| Runtime-синхронные `mem_write/patch/erase`, loops `sync_finish/log_wait` вне старта, direct W25 из обработчиков; повторное чтение boot-error и самостоятельный polling из user_loop | Драйвер W25 с WREN, таймаутами и проверкой каждой записи/стирания; ASM CRC с измеренным выигрышем; CRC базы ID только в RAM |
| CRC-макросы подмены W25 и владение полями `w25_job` из разных модулей — один внутренний pipeline записи ID | `work_memory`/USB lifetime, epoch отмены, сохранённые upload cursor и маркеры очистки; память in-flight буфера до конца verify |

Стартовые синхронные API можно оставить приватными для `user_init`, до включения runtime. Поведение сектор-журнала/A/B/W25 не переписывать; перенести только планирование и потребителей результата. Реальную неисправность SPI (`spi_ready()==0`) и превышение времени **запущенной** физической операции отличать от ожидания чужого запроса; `!w25_read_available()` само по себе не повод бесконечно ждать или сообщать IO_ERROR. При неопределённом результате проверки не запускать другого писателя.

## 6. Порядок реализации

Каждый шаг — самостоятельная рабочая версия, проверяется `Tests/check.py --full` **до следующего шага**, обе конфигурации и загрузчик. Одна папка результатов `%TEMP%\domovoi-flash-build`; не запускать два отдельных прогона одновременно. Прежние тесты менять только при обоснованной замене контракта, а не для маскировки регрессии.

| Шаг | Результат и проверяемый предел |
|---|---|
| 1 | Добавить one-job/submit/completion и единый статус ожидания, перевести существующие 12 типов под один switch с временными адаптерами; объединить физический pipeline/CRC. Сохранить старые приоритеты/форматы на первом переходе; новые инварианты владельца, RAM/lifetime, отмена. `--full`. |
| 2 | Перенести confirm/rollback/boot-error/установку FW; mailboxes и reset-барьер. Убрать синхронный app-update runtime-путь, 133 при ожидании, повторное чтение boot-error. Реальный серверный вход, 30 мин, питание и настоящий IO-отказ. `--full`. |
| 3 | Перенести ID/group/schedule/scenes и temp-ID; приём Wiegand независимо от флеш, диапазоны согласованности, приоритет доступа/счётчик до реле. Исправить E01/E02, измерить оба варианта ID-поиска и блокировку на sector commit. `--full`. |
| 4 | Настройки/save/reset/factoryReset и manual-stage → requests/results; удалить синхронные runtime-записи. FactoryReset не обещает завершение до OK; ошибка/питание проверяются явно; RAM writer получает эксклюзивный переход. `--full`. |
| 5 | Отделить транспортные ответы от flash-job, удерживать готовые сервер/USB-кадры, завершить bounded queue/backpressure/приоритеты журнала и фона; исправить E03/E06, проверить starvation и epoch. `--full`. |
| 6 | Удалить старые owners/active/gates/CRC-макросы/адаптеры и недостижимые sync-runtime API. Проверка всех callsites, BIN/MAP/стека, dead-code без новых необоснованных исключений, протоколы 212×2, все power-cuts. `--full`. После этого отдельно проверить отклик/нагрузку/питание на плате по согласованному сценарию. |

Порядок: **единое состояние → FW/проба → доступ → настройки/сброс/ручной загрузчик → транспорт/журнал → удаление старого диспетчера**. Форматы долговечного хранения и проверенный W25-драйвер сохраняются на всех шагах.

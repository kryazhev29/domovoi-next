## 3. Слои и контракты

Предлагаемые файлы: `Modules/comm_uart.*`, `Modules/comm_at.*`, `Modules/modem_{slm336,m66,eg915}.*`, `User/comm_channel.*`, `User/comm_server.*`, `User/comm_diag.*`. Все сроки и интервалы — только `User/comm_timeouts.c`; профили типов хранят ссылки/индексы в эту таблицу.

UART не знает AT; AT не знает сервер; драйвер знает синтаксис модема; канал знает TCP и восстановление; серверный адаптер знает регистрацию, статус и адреса. Будущий WiFi реализует тот же интерфейс канала и использует тот же IMEI, без изменения SLDN. Выбор/переключение WiFi сейчас не реализуется.

Прототипы ниже — проект контрактов, не готовые исходники. Контексты и enum имеют фиксированные целочисленные поля, без зависимости wire-форматов от размера C enum.

`comm_at_request_t`: указатель/длина команды, тип ожидаемого ответа, ID срока, обработчик заголовка/результата. Двоичную длину задаёт **проверенный заголовок QIRD**, а не произвольная URC или наличие SLDN. AT parser: LINE → PROMPT либо BINARY(n) → LINE/FINAL; в BINARY ни NUL, ни CRLF, ни OK/ERROR/RING не имеют управляющего смысла. `OK` сопоставляется целой строкой; `>` — отдельной грамматикой. Разрывы возможны после любого байта. Эхо учитывается до ATE0.

`+QIURC: "recv",id` только выставляет признак данных. Читать QIRD повторно до опустошения: SLM не обещает новую URC, пока старые данные не вычитаны. M66: команда `AT+QINDI=1`, уведомление **`+QIRDI: id,sc,sid`**, чтение `AT+QIRD=id,sc,sid,len`; заголовок содержит remote IP/port, тип и фактическую длину. Это иной формат, чем `+QIRD: n` у SLM.

Ping считается успешным при фактическом получении ответа (`rcvd > 0`), а не по начальному OK или нормальному завершению процедуры: итоговый код у SLM — 0, у M66 — 2, при этом ответы могли все потеряться. DNS также ждёт результата/IP после OK: SLM выдаёт `+QIURC: "dnsgip"`, M66 — IP либо ERROR/STATE. Нормализовать эти различия в драйвере.

Без очереди копий UART/TCP/кадров и без выделения памяти в ISR/AT. UART-кольцо — транспортный запас, существующий SLDN-буфер — один собираемый кадр. QIRD ограничивается вместимостью потребителя; при backpressure новые чтения не запускаются. Серверный handler вызывается после освобождения UART-участка. AT завершает событие в main, callback не вызывает следующую AT рекурсивно.

Overflow/ошибка UART внутри тела инвалидируют всю текущую операцию и сессию: не искать следующий OK внутри обрезанного payload и не продолжать склеивание. Переполнение строки также является явной ошибкой; неизвестные корректные URC сохраняют границы parser, но не подтверждают команду.

TX использует память отправителя до физического UART TC и завершения QISEND. SEND OK означает приём модемом, TCP ACK — доставку TCP, ответ команды сервера — отдельное подтверждение. При обрыве и смене поколения все старые TX/события отменяются; прежние правила повторов фото/журнала/FW сохраняются. Сырой указатель на стек или освобождённый malloc в новый UART не передаётся. Согласование единого TX-слота и SMS — Q1/Q2.

Один `poll` разбирает ограниченный объём уже принятых байтов и запускает только готовое действие; срок не означает ожидание в цикле. Время — монотонные `uint32_t` мс, проверка разности с учётом переполнения; пропущенные тики не замедляют сроки. WDT обслуживает общий main, AT-драйвер его не «кормит» в ожидании. Звонок/ATH имеют приоритет перед новой фоновой командой; уже работающую долгую AT прервать безопасно не всегда возможно — Q3.

## 4. Автомат выхода на связь

| Шаг | Успех → следующий шаг | Ошибка/срок → переход |
|---|---|---|
| OFF / DISCHARGE | По разрешённому сроку запуска → POWER_STAGE1 | Остаётся автономная работа; новая попытка не отменяет паузу |
| POWER_STAGE1 → POWER_STAGE2 | По профилю платы, без ожидания CPU → AT_READY | Ошибка питания/нет ответа → физическое OFF, backoff |
| AT_READY | Валидный ответ AT; при пустом типе GMM и сохранение один раз → SETUP | Молчание → OFF, 10/30/60 мин. Посторонняя URC не является ответом AT |
| SETUP | Эхо/URC/UART, SIM1/hotplug, CLIP, режим buffer; IMEI если ещё нужен → SIM | Ошибка обязательной команды → причина и контролируемое восстановление |
| SIM | Прямой запрос выбранной SIM1: READY → NETWORK | NOT INSERT → WAIT_SIM, опрос 60 с; PIN/PUK → отдельная причина, не угадывать PIN |
| NETWORK | CREG/CGREG/CEREG согласно типу и RAT → PDP | Нет регистрации → WAIT_NETWORK; питание не чаще 30 мин при живом модеме |
| PDP | Проверить/настроить APN при необходимости, активировать и проверить IP → TCP | Повтор; две неудачи активации → OFF с установленными паузами |
| TCP | Открыть основной/выбранный резервный endpoint; дождаться результата socket, не только OK → SERVER_REG | Быстрый повтор; после трёх неудач основной адрес → резервный, если разрешён |
| SERVER_REG | Существующий кадр регистрации сразу после TCP; команда 1 CMD_SUCCESS → ONLINE | Нет ответа → повтор регистрации, затем TCP; явный отказ хранится отдельно от «нет интернета» |
| ONLINE | Статус 15 с; валидный ответ сбрасывает пропуски | Три пропуска → CHECK_PING; закрытие TCP/подозрение на обрыв 2G → TCP сразу |
| CHECK_PING / CHECK_DNS | Проверка ya.ru успешна, сервер молчит → SERVER_SILENT | Ping неуспешен → DNS; обе проверки неуспешны → REOPEN_TCP |
| SERVER_SILENT | Повтор регистрации/связи с разрешённым адресом; валидный обмен → ONLINE | Событие 13 один раз; нарастание пауз, без сброса PDP/питания из-за молчания сервера |
| REOPEN_TCP → REACTIVATE_PDP → OFF | На первой успешной ступени → SERVER_REG | Не помогла ступень → следующая. CPU reset отсутствует |

WAIT_SIM/WAIT_NETWORK/SERVER_SILENT не блокируют ID, входы, выходы, USB, журнал и доступные звонки. При отсутствии SIM/покрытия звонок физически недоступен; это не ошибка автономной базы. Настройки ручного APN/RAT имеют приоритет; алгоритм автоматического выбора и его пороги ещё требуют Q5.

Ортогональный автомат звонка: IDLE → ANSWER_REQUEST → NUMBER_CHECK/OPEN_ONCE → HANGUP_DUE(1 с) → DATA_GRACE(10–20 с) → IDLE. Если номер ещё не пришёл, сохраняется состояние одного вызова и ожидается CLIP; при повторных RING/CLIP повторного открытия нет. Новый вызов также проходит существующую `tPause` выхода. Во время звонка/восстановления данных не накапливать пропуски статуса и не начинать recovery из-за них; подтверждённое физическое закрытие socket учитывается, переоткрытие согласуется с завершением звонка.

Суточный перезапуск модема: одно отложенное намерение на сутки; ночью только при отсутствии звонка, незавершённой AT/TX/RX и обмена фото/журнала/FW. Отложить при занятости; рост ошибок может запросить более ранний перезапуск. Ночное окно, отсутствие RTC и порог ошибок — Q6. Не использовать `config.restartTime` как таймер модема без решения архитектора.

## 5. Единая таблица сроков

Единицы будущей `comm_timeouts.c` — мс (`uint32_t`), счётчики попыток отдельно. Поля «из предложения» — исходные пределы для согласования/замеров, не пределы возможностей модема.

У каждой попытки фиксировать начало и фактическую длительность каждого измеряемого шага, включая неудачный; итог шести основных фаз показывать отдельно. В кандидате 16 шагов: разряд, питание 1/2, AT_READY, определение типа, базовый UART/AT, URC, SIM/hotplug, VoLTE, IMEI, проверка SIM, выбор сети, регистрация сети, APN/PDP, TCP, серверная регистрация. Команды внутри шага выполняются последовательно; время последней AT доступно отдельно. Около 10 с — цель обычного пути, не суммарный аварийный deadline: 2–3 + ≤1 + 2–5 + ≈1 + ≤1 + ≤1 = примерно 7–12 с. Продолжать сразу после ответа; тип не опрашивать при заполненном поле, сохраняемые настройки модема не переписывать без изменения. Неизбежные volatile-настройки выполнить один раз на запуск. IMEI/служебные опросы не задерживают регистрацию, если уже есть достоверные данные.

При AT timeout запрещено считать движок свободным и отправлять следующую команду поверх предыдущей. Нужна граница завершения/ресинхронизации либо физическое снятие питания; поздние OK/QIOPEN не переводят новую попытку в успех. Сам номер поколения в RAM не различает два одинаковых запоздалых ответа модема — Q3.

## 7. Пробный запуск и откат

**Уже реализовано:** `app_boot_metadata` восстанавливает trial из BOOT_JOURNAL; `app_trial_confirm` пишет/проверяет точный ноль в `BOOT_JOURNAL_CONFIRMED`; `user_parse_comand`, команда 1 CMD_SUCCESS только с CH_SERVER, подтверждает пробу и пишет событие 136. `app_trial_expired` имеет срок **1800 с**; `user_loop` по нему запрашивает откат и reset. `boot_core.c` хранит маску запусков, разрешает **3 запуска**, затем возвращает резерв; явный rollback также ведёт в этот путь. Сектора/смещения и backup не меняются. События 132–137 и глобальный срок докачки FW 600 с сохраняются.

Удаляется только вызов `app_trial_rollback(); user_savereset();` из GSM_POWEROFF. У действующей подтверждённой FW нет перезагрузки из-за связи. У пробной FW остаётся существующий независимый срок пробы и boot-лимит запусков; watchdog/reset/power loss не стирают подтверждение, журнал или резерв. Это **reset для выполнения процедуры отката обновления**, а не ступень восстановления модема; загрузчик физически запускается только после reset.

Новый канал сообщает успех регистрации прежнему обработчику; ни TCP-open, ни SEND OK, ни ping не подтверждают новую FW. Пока проба активна, не принимать установку поверх её журнала/backup. Неудачная запись подтверждения оставляет trial активной; следующий успешный ответ повторяет подтверждение.

**Несогласованная развилка Q8:** строка 126 таблицы требует три попытки с текущими настройками и по попытке каждого автоматического варианта. Это не boot-лимит трёх запусков. Нынешний GSM-счётчик тоже не обеспечивает эту последовательность. Удалять ограничение 1800 с, вводить ранний откат по новым правилам или расширять его на цикл 10/30/60 мин без решения нельзя. Сценарий «новая FW, SIM отсутствует» и необходимость reset для отката должны быть подтверждены отдельно от правила автономной работы обычной FW.

Предложение также требует сохранять журнал/разблокировку перед reset и восстановить реле первыми. `user_savereset` сохраняет журнал/device, но это не доказывает восстановление физического выхода после WDT/PVD. В просмотренных `main/user_initvariables/outs` явного восстановления разблокировки до запуска модема не найдено; event 39 по PVD уже есть. Не добавлять эту отдельную логику в связь молча — Q9.

## 8. Бюджет памяти

### Исходные ограничения

MCU: 128 КиБ внутренней Flash, 20 КиБ RAM. Для кода приложения: `0x08020000-0x08008200 = 97 792` байта; заголовок отдельно 512 байт. По зафиксированной карте `docs/history/MCU_AUDIT_FOLLOWUP.md` обеих конфигураций: readwrite DATA 19 516, readwrite CODE 636, CSTACK 4096, HEAP 5120; heap limit `0x20004E90`, fault_record `0x20004FC0`, щель **304 байта**. CSTACK/HEAP уже входят в readwrite DATA, повторно не прибавлять. Это исходная опубликованная карта, не новая сборка этапа 0.

Точно удаляемые массивы: GSM RX 2048 + `gsm_strbuf` 128 = **2176 байт static**. Плюс удаляемые GSM/UserGsm/ucon/UART-поля — только по map, не по комментариям размеров. Heap-строка AT сейчас до 2048+16=2064 байт полезного запроса плюс allocator; нового аналога не планируется. Это отдельный пик, его нельзя прибавлять к статической экономии или к несопадающим по времени пикам. Существующие server RX 2048, USB TX 1280, log_pending 512 сохраняются.

### Расчёт кандидата по слоям

Это плановые размеры контекстов/лимиты, не `sizeof` написанного кода. Дополнительная SMS-память и решения Q1/Q2 пока в расчёт не включены.

| Слой | Static RAM, байт | Расчёт / предел Flash, байт |
|---|---:|---|
| UART модема | 536 = кольцо 512 + контекст 24 | 160 инструкций×4 + 128 таблиц/констант = 768 |
| AT | 360 = команда 128 + строка 192 + контекст 40 | 700×4 + 272 = 3072 |
| Драйвер SLM336 | 64 активного контекста, общий для типов | 380×4 + 1040 строк/таблиц = 2560 |
| Драйвер M66 | 0 дополнительно к общему контексту | 220×4 + 656 = 1536 |
| Драйвер EG915 | 0 дополнительно к общему контексту | 300×4 + 848 = 2048 |
| Канал | 24 | 100×4 + 112 = 512 |
| Адаптер сервера | 32; старый RX 2048 отдельно и без прироста | 140×4 + 208 = 768 |
| Recovery/звонки | 16 | 250×4 + 280 = 1280 |
| Диагностика/сроки | 216 = header 24 + 16 длительностей×4 + 10 сбоев×12 + индексы 8 | 130×4 + 248 = 768 |
| Один новый постоянный TX-слот | 1900 | Действующий максимум gsm_senddata; лог до 32 записей: 32×32+14=1038; фото 512+22=534; регистрация 48 |
| **Всего кандидата** | **3148**, включая TX; **1248** без TX | **13 312** новых Flash, до вычитания старого GSM |

Flash-оценка использует верхнюю ширину Thumb-2 4 байта и плановый объём логики/констант. Это инженерный лимит для сверки по map, не предсказание оптимизатора IAR. Существующий протокол/boot сюда не включён. Формула: `F_after = F_baseline - F_removed_gsm + F_new`; измерить baseline и вклад старых объектных файлов необходимо до этапа 1. Исходный размер Flash этой копии пока не измерен из-за отказа IAR build.

Для RAM кандидат с постоянным TX даёт `3148-2176=+972` байта **до** удаления старых контекстов; доступно 304. Необоснованно считать, что поместится: старые контексты должны освободить минимум **668 байт**, либо нужен иной согласованный вариант. Без постоянного TX static сокращается минимум на `2176-1248=928`, но удержание malloc до TX требует heap-расчёта: прежний наблюдённый пик фото **4864/5120** не оставляет ещё 1900 байт. Одновременно работающая камера/Flash writer и передача проверяются обязательно. Резервы стека/heap не уменьшаются по предположению. Q1/Q2 — обязательная развилка бюджета, а не скрытый «запас».

Кольцо 512 — кандидат: при 115200/10 = 11 520 байт/с полезные 511 байт покрывают **44,36 мс** непрерывного поступления. Чтение QIRD кусками 256: `256 тела + ≤50 заголовка + 6 хвоста + ≤192 одной URC = 504 < 511`. Это расчёт одного ограниченного burst, не доказательство при нескольких URC или длинной Flash-операции. Общая формула `RX >= ceil(11520×T_main_max/1000)+burst_margin+1`; `T_main_max` надо измерить. При недостаточности пересчитать размер, не молча терять байты. Команда 128 получается из нынешних полей APN/login/pass до 30 символов, ограниченного endpoint и форматирования; строки/SMS длиннее 192 требуют отдельного решения, не обрезать управляющую команду до исполнения.

Перед каждым этапом считать включаемые/удаляемые массивы, контексты, константы, максимальный живой heap и вложенность стека. После — две IAR map, Flash/RAM delta по объектам, проверки границ fault_record и boot/app, stack/heap тесты. Статическая экономия не доказывает достаточность heap, а успешная линковка не доказывает достаточность стека.

Журнал SLM336 воспроизводит: GMM/AT READY, SIM1 NOT INSERT, SIM2 NOT INSERT посреди ответа CREG, сдвиг ответов CREG/CGREG, состояния 0/3/2, два power cycle и старый Reset cpu. Новый ожидаемый результат: WAIT_SIM, опрос раз в минуту, main работает, нет reset CPU и ложной ошибки по SIM2.

Журнал M66: Call Ready внутри ответа, QNITZ/CTZV/SMS Ready, CREG 2→1, CGATT CME ERROR 100 с последующим CGREG 1, CONNECT OK, QISEND 48/SEND OK, серверный кадр 16 байт и старый Factory reset. Нельзя считать временный CME ERROR окончательной потерей сети. Точный серверный код из отладочного лога с обрезанным бинарным телом не восстановить; новый QIRD-ответ/успешную регистрацию добавить отдельными синтетическими fixtures, не выдавать за реальную запись. Судьба factory reset на отказ регистрации — Q10.

Логи содержат USB-обрамление SLDN, отладочные префиксы и повтор одного ответа в Answer/Recv, без достоверных времен каждого байта. Имитатор выделяет направление/AT-ответы, не скармливает отладочный текст как URC; сохраняет происхождение fixture. Timing/разрывы/склейки задаются отдельно. Документация не заменяет проверку конкретной версии модема.

### Фактическая проверка этапа 0

Изменений прошивки нет; Flash/RAM delta кода **0/0**. В этой копии прошли все 43 уникальные non-TX host-группы + группа TX с пятью сценариями, SMS debug и `Bootloader/tests/run_tests.py`. Zig cache направлен в ignored `Release/comm-stage0`, глобальное окружение не изменялось.

IAR Release и Release_IPv3 пытались собрать: сборщик остановился на разрешении пути `/Modules/adc_stm32f10x.c`; попытка абсолютного/короткого пути Release дала `weakly_canonical` на пути объекта. Свежих ELF/map нет; IAR-эмуляция не выполнена (в доступном bundled Python также отсутствуют unicorn/pyelftools). Исторические PASS из аудита не выдаются за новый прогон. Логи — ignored `Release/comm-stage0`. Плата, COM, сервер и другие worktree не использовались.

Оформление коммита заблокировано средой: `git add` не может создать `index.lock` в Git-каталоге собственного worktree, расположенном вне разрешённого корня записи. Индекс/HEAD не изменены; документ остаётся единственным новым рабочим файлом.

## Вопросы архитектору

1. **TX и вместимость RAM.** Разрешена ли механическая замена stack/malloc назначения `user_send_*` и `photo_send` на один сохраняемый TX-слот, без изменения байтов/алгоритмов протокола? Как обслуживать второй ответ при занятом слоте? Лимит 1900 сохранить? Постоянный слот пока не укладывается в доказанный бюджет; malloc-конструкция требует проверки пиков. Нужен согласованный вариант до подключения протокола.
2. **SMS и размер UART.** Сохраняем весь существующий SMS/USSD/NTP функционал; разрешено ли потоковое выделение нужных полей SMS вместо передачи полной строки старому `user_smsreceived`? Какие поддерживаемые размеры/кодировки? Дополнительный большой SMS-буфер не посчитан. Для кольца 512 нужны измеренные main gap/burst и подтверждение порога переполнения.
3. **Долгие AT.** Принять пределы предложения PDP 20 с/TCP 10 с или документированные 150 с? Что делать с поздним результатом, когда модем ещё не разрешает следующую AT, и как обслужить ATA/ATH в этот момент? Нужна политика soft deadline/resync/cancel по каждому типу, без угадывания возможности прерывания. Также нужны короткие AT/prompt/send/ping/DNS/close сроки.
4. **Ретраи и 2G.** Сколько повторов SERVER_REG перед новым TCP; какие интервалы нарастания для сети/молчащего сервера и когда обнулять ступени? Что считать подозрением на silent drop 2G без URC, не обходя правило трёх пропусков/ping? Как чередовать основной/резервный после трёх неудач каждого?
5. **APN/RAT.** Какой источник «профиля SIM» считать допустимым: автоматический APN модема или конкретные данные SIM? Какие варианты перебора сети/оператора, пороги ошибок/сигнала и сроки возврата 4G? Значения вручную не подменять автоматически.
6. **Питание и суточный restart.** Нужны сроки/полярности по профилям, ночное окно, правило без достоверного времени и при многосуточном обмене, порог раннего перезапуска. Менять ли существующую настройку `restartTime` перезагрузки контроллера? Автоматически переиспользовать её для модема нельзя.
7. **Тип/SIM1.** Как совместить сохранённое `M_UG95=1` (сейчас также EG915) с новым отдельным EG915, оставить ли UG95? Нужно ли отличать аппаратную замену при заполненном поле без опроса GMM? Подтвердить SIM1-запрос и hotplug для SLM336E: Common описывает SIMHOTSWAP, EX — QSIMDET/QSIMSTAT, явного селектора SIM1 в просмотренных разделах нет. Нужен TCP/IP manual точного EG915 и факт его профиля питания. Подтвердить публичные дополнительные соединения: сейчас ucon[4], реально используется один серверный.
8. **Trial.** Сохраняем независимые 1800 с + три boot-запуска или подключаем ранний откат по строке 126? Перечислить автоматические варианты и критерий исчерпания. Подтвердить, что reset ради исполнения запрошенного отката разрешён при неуспехе пробы, включая отсутствие SIM; обычная FW остаётся автономной.
9. **Реле/дубли при reset.** Требование предложения о восстановлении разблокировки после WDT/PVD и защите от повторной команды при потерянном ACK считать отдельной работой или включать в эту интеграцию? Сохранение device не доказывает оба поведения; нужен утверждённый сценарий, особенно при обновлении/откате.
10. **Отказ регистрации сервера.** Оставлять существующий factory reset обычной FW на REG_UNKNOWN_IMEI/REG_NOT_BOUND? Лог M66 показывает Factory reset после ответа. Это влияет на автономную базу, но относится к сохранённому обработчику протокола; самостоятельно менять его нельзя.

Номер/формат новой USB-команды предлагается отдельно на этапе 7, как поручено. До разрешения архитектора реализация не начинается.

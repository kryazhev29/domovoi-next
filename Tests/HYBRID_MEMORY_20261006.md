# HYBRID_MEMORY_20261006 — результат этапов B–E

База `51e207a`, логика исходной базы `d9e3dd5`. Работа локальная, без устройства и сервера, без коммитов по поручению владельца. План принят ранее: [таблица функций и исходные оценки](../docs/hybrid_memory_plan.md).

HYBRID: **BIN 88765 Б**, свободный промежуток ОЗУ **2184 Б**. Цель BIN ≤87633 не достигнута на **1132 Б**, ОЗУ ≥3072 — на **888 Б**. Функции не урезались. От исходного C BIN меньше на 2964 Б, от ASM — на 3952 Б; запас ОЗУ вырос на 2120 Б.

## Проверки и воспроизводимость

- IAR EWARM 9.50.1.380, Release High/Size: ASM/C/HYBRID — 0 ошибок. Stack analysis включён; Ls014/Ls016 остаются по причине ниже.
- `run_all --project ASM|C|HYBRID`: **71/71 для каждого**, включая мутации и обрывы питания. Перед изменениями свежие C/ASM: 67/67; первичный HYBRID: 67/67.
- Парное сравнение ASM/C/HYBRID: **198 сценариев, 0 расхождений**. Сохранённые `result`/`returned` исходного ASM также совпали во всех 198 сценариях всех вариантов; новый код не сравнивался только с самим собой.
- Горячие полные пути карта → GPIO и сервер → commit проверены отдельно; таблицы ниже. Это инструкции Unicorn, не DWT и не проверка платы.
- Владение: 196 упорядоченных пар, 50 допустимых; запрещённые пары получают отказ без изменения данных. Реальные FW/config handoff, photo/upload ACK/retry/cancel и 25 одиночных IRQ-вставок проверены.
- Форматирование: 2097152 STATUS случаев, все сетевые значения/сигнал/флаги, все ushort firmware × флаги; границы u32/i32/hex и 100000 дополнительных значений, NUL и canary. Linked ELF проверяет ABI STATUS с семью аргументами в стеке и scalar boundaries. `__iar_small_memcmp`: 704 комбинации длины/выравнивания/различий и NULL при n=0.
- USB: 420 комбинаций границ/PRIMASK/reset, атомарность публикации и backpressure; максимальный ответ 1038 Б не публикуется при свободных 1037, принимается после освобождения 1038.

Python — `%TEMP%/codex-py311/python.exe`, зависимости — `%TEMP%/codex-deps`, Zig — `DOMOVOI_ZIG`, оба Zig cache перенесены в TEMP. IarBuild `-build` не проходит sandbox canonicalization; `Tests/build_iar.py` выполняет реальные команды IarBuild `-jsondb`, включая assembler/compiler/linker/ielftool. Это успешная сборка IAR-инструментами, не утверждение об успешном wrapper `-build`.

Последняя правка CFI/пробелов меняет метаданные ELF; три проекта пересобраны, BIN SHA-256 побайтно прежние. Связь финальных BIN с образами полного прогона записана в JSON; свежий ELF HYBRID дополнительно прошёл workspace/access/formatter. Независимые полные три-проектные прогоны после каждого промежуточного C/D подшага не заявляются: полный набор выполнен для окончательной совокупности изменений.

Плановые ~190 Б были нижней оценкой независимого выбора модулей. PHOTO означает context+packet при допустимости обоих. Остальные shared роли взаимоисключаются. Пик допустимых наборов укладывается в 2032 Б shared; FW context/data+PHOTO_PACKET заканчивается по 1686, upload+photo — 1614 с выравниванием. Большие REPLY/SMS/TABLE используют shared отдельно, PHOTO_CONTEXT сохраняется.

Прежний NULL теперь означает занятую область/превышенный предел и оставляет прежний отказ протокола. Повторное получение той же роли запрещено; неверный pointer/role при release не снимает чужое владение. Tests/test_work_memory проверяет все 196 пар, границы, canary и независимое release; реальные автоматы проверены ELF lifetime/owner tests.

Upload ACK: предварительный резерв context+packet отдаётся перед durable config snapshot; false означает повтор ACK после сохранения, true не запускает config и повторно берёт те же адреса до инициализации. Это необходимо для реального ACK при сохраняемом photo-context, а не только синтетического acquire. FW отдаёт reserve перед CONFIG, сохраняя context. NOR/wire сравниваются с исходным образом.

## Стек и USB

IAR без полного графа: основная цепь ASM/HYBRID 2376 Б, C 2216 Б; максимальная IRQ-цепь 144, сумма IRQ roots 256 во всех трёх. `(2376+256)*1.25`, округлённое к 8, равно 3296 Б (аналог C 3096), но использовать это как доказанный размер нельзя: косвенные вызовы и все допустимые вложения IRQ не закрыты. `settings/runtime_stack.suc` — отключённый кандидат из 48 callback связей, полнота не сертифицирована. Две квалифицированные попытки линковки (включая recursion depth) закончились внутренним AccessViolation 0xc0000005, чтение 0x8; третьей попытки не было. Поэтому Ls014 (ASM/HYBRID) и Ls016 (все три) объяснены, не скрыты.

Группировка NVIC меняется: board.c:105 group0, uart_stm32f10x.c:438 group1, hw_config.c:170 group2; USB LP priority2/wakeup0, WG priority0/sub1, UART priority1/sub7, SysTick — низший. Только сумму IRQ roots нельзя объявлять худшим вложением при всех этих состояниях.

Наблюдение раскраской A5A55A5A и min-SP на обёрнутых вызовах полного run_all/paired/full paths:

| Проект | Вызовы | Пик по SP, Б | Пик записи раскраски, Б | CSTACK, Б |
|---|---|---|---|---|
| ASM | 1079518 | 1368 | 1312 | 4096 |
| C | 1071516 | 1360 | 1304 | 4096 |
| HYBRID | 1071482 | 1360 | 1304 | 4096 |

Это наблюдённый максимум модели, не доказательство всех вложений NVIC; IRQ helper резервирует синтетический frame 32 Б. Отдельные 25 IRQ-вставок дали максимум 224 Б и точное сохранение owner/NOR. Стек **4096** оставлен: `0x20003738…0x20004738`, fault_record `0x20004FC0`, 48 Б. Искусственный MSP=0x20000000 приводит к UC_ERR_WRITE_UNMAPPED, fault_record не изменён; Unicorn не исполняет автоматическую fault stacking/escalation. Управляемый отказ/сброс вместо lockup не доказан — перенос в начало ОЗУ не выполнен по решению владельца.

USB TX 1040 Б (доступно 1039), максимальный пакет журнала 1038, ID 1014, config 523, photo 534. RX 2048 оставлен. Общий `User/usb_ring_size.h` используется hw_config и обоими writers; reset/PRIMASK/атомарная публикация сохранены. Экономия **240 Б**, не ожидавшиеся 1024. Старый host тест с photo 1046 исправлен: production PHOTO_BLOCK=512, photo пакет 534; граница теперь реальный log 1038.

PMA — только оценка: отказ от TX ring освободил бы 1040 Б; метаданные source/offset/epoch займут ориентировочно 16–32. Если источник удерживается в существующей памяти, потенциально остаётся ~1008–1024 Б и запас 3192–3208. Дополнительные копии временных пакетов уменьшают этот выигрыш; для stack-пакетов требуется отдельное решение. Необходимы transport ownership до последнего IN, chunking, reset cancellation и backpressure. Это не реализовано и в итоговую память не засчитано. Неизменяемые таблицы/строки уже RO; новый capacities[] тоже const, отдельного выигрыша не заявляется.

## E1. Загрузчики: расчёт без правок

| Артефакт | Код, Б | RO data, Б | Полезный RO, Б | BIN, Б |
|---|---:|---:|---:|---:|
| Новый, текущий Bootloader/ (свежий IAR) | 15892 | 484 | 16376 | 32768 |
| Старый загрузчик | н/д | н/д | н/д | н/д |

Для старого загрузчика нет доступной пары map/BIN в этом worktree. Приписывать ему размер 32768 как размер кода нельзя. Для нового BIN имеет 32768 из-за footer по 0x08007ffc, а полезный RO 16376. Чтобы уложить полезный код+данные в 8192, требуется убрать не менее 8184 Б (ещё без учёта размещения/выравнивания). Сам факт пустой части текущего BIN не делает загрузчик 8-КБ.

Крупнейшие связанные модули нового загрузчика:

| Модуль | Flash, Б |
|---|---:|
| usb_core.o | 2962 |
| boot_platform.o | 2344 |
| boot_core.o | 2256 |
| boot_main.o | 1352 |
| sector_journal.o | 912 |
| usb_prop.o | 786 |
| usb_regs.o | 718 |

При неизменных header 0x08008000 и vectors 0x08008200 освобождение места **для приложения равно 0 Б**: ROM начинается по прежнему адресу. В отдельном радикальном проекте перенос header в 0x08002000, vectors в 0x08002200 увеличивает приложение с 97792 до 122368 Б, то есть +24576 Б (32К−8К), при условии сохранения 512-Б header. Это расчёт, адреса в репозитории не менялись.

Нужны SWD/ST-Link для первичной замены загрузчика и восстановления, отдельная проверка установки/rollback/оборванного питания и USB recovery. Потребуется пересобрать приложения и проверить BootHeader magic/HW/CRC, переход по новым векторам, BOOT_MAX_CODE, app_boot_request, ручной RAM writer и footer/version ABI. Сейчас board.h:20,26,30 вычисляет BOOT_VER относительно конца 32-КБ boot, а boot_manual.c:21,24 проверяет PC и footer старой области. Сохранение footer 0x08007ffc мешает отдать всю разницу приложению.

В текущих Bootloader/ и C/ASM runtime явного BKP_DR10-контракта не найдено; нынешний boot_main:104 выбирает режим по кнопке, boot_run и валидности приложения. Для совместимости с установленным старым boot нужно отдельно получить его реализацию и сохранить значения/очистку BKP_DR10; совместимость не доказана. BKP_DR1 сейчас занят причиной PVD reset (board.h:24), подменять им DR10 нельзя. Ничего в загрузчике/обновлении не исправлялось.

## Что не получилось

- Обе цели HYBRID не достигнуты: 1132 Б сверх лимита BIN и 888 Б недостающего ОЗУ. C достигает лимита BIN (86729), память всех трёх одинакова.
- Полный .suc/IRQ proof и перенос стека не получены: внутренний сбой IAR и недостаточная модель fault escalation. Стек сохранён 4096 на прежнем месте.
- MFC не дал образа из-за существующего конфликта типов; PMA не реализовано, старый bootloader map/BIN недоступен.
- Выигрыш гибрида по размеру оказался отрицательным относительно ASM; основная выгода — скорость карты при сохранении быстрых ASM горячих групп. Неизмеренные экономии не засчитаны.

Устройство, сервер, платежи/SMS/команды доступа, заводской сброс и прошивка не запускались. Загрузчик/ROM/протокол/NOR/DWT не изменялись. Коммиты не создавались по прямому поручению владельца.

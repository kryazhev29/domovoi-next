# Команда 14: расписания по 16 Б, 06.10.2026

База — `compare/c-asm`, `22b23f9`. Локальные изменения без коммита.
Плата, сервер и копия для передачи не использовались. План создан до кода:
[`docs/sched16_plan.md`](../docs/sched16_plan.md).

## Формат и хранение

Сверено с `docs/protocol/protocol2.md`: ИЗМЕНЕНИЯ, строка таблицы 29;
команда 14, строки таблицы 308–339; ответ 5, строки 494–501; ответ 11,
строки 546–552; ответ 12, строки 554–559. Полезные данные: таймштамп LE32,
N (1–64), N записей по 16 Б, общий хвост 16 Б. Строго `21 + 16*N` Б;
максимум 1045 Б. Неверные длина, N или индекс дают ответ 11, команда 14,
код 1 («ошибка параметра»). Успех — ответ 12, тип таймштампа 3, таймштамп
пакета и CRC16. Ошибка хранения — прежний код 2.

`MB_SHEDULE` остаётся `0x1CA800`, 2048 Б:

| Смещение | Содержимое |
|---|---|
| 0–1023 | 64 ячейки по 16 Б; пустая ячейка полностью FF |
| 1024–1039 | scene[8], onHoliday, reserve[7]; до первого пакета FF |
| 1040–2047 | FF |

Запись идёт по индексу 1–64; ячейки, которых нет в пакете, стираются в FF (пакет несёт все расписания контроллера; решение 06.10 — иначе удалённое на сервере расписание оставалось бы в контроллере и CRC команды 17 не сходилась). Повторяющиеся
индексы сохраняют прежнее правило: последняя запись побеждает. Хвост заменяется
целиком. Записи и хвост публикуются одной существующей журнальной транзакцией
сектора `0x1CA000`; его первые 2048 Б сохраняются. Резервы пакета сохраняются
побайтно.

CRC16/MODBUS: начальное значение FFFF, отражённый полином A001, без финального
XOR. Обрабатываются ровно первые 1040 Б блока, включая FF пустых ячеек и хвост.
Правило длины находится **в одной строке**, `sched16_crc_size()` в
`User/table_runtime.c`; её используют ответ 12 и оба пути команды 17 во всех
вариантах. CRC расписаний в ответе 5 на команду 17 — байты 13–14 полного SLDN.
Протокол эту область CRC пока не закрепляет: реализовано предложение задания.

`WORK_TABLE` в исходном HEAD уже имеет ёмкость 2032 Б, а не 1024 Б. Копируются
только записи с хвостом, максимум 1040 Б; таймштамп и N хранятся в существующих
полях автомата. `work_memory_s` остаётся 2224 Б. Постоянная RAM не добавлена.
Полный входящий SLDN-пакет занимает максимум 1056 Б; существующие входные
буферы сервера и USB по 2048 Б достаточны. Кольцо USB TX не расширялось:
ответ 12 занимает 18 Б.

## Переход и питание

Маркер `SH16` (`0x36314853`) и его побитовая инверсия занимают ранее свободные
`device.reserv[32..39]`. Размер device не меняется; маркер защищён его CRC и
существующими атомарными слотами конфигурации. Резервы 0–31, уже занятые
указателями и журналом, не меняются. Маркер не входит в расписания или их CRC.

После восстановления журнала и блока устройства реальный `user_init` вызывает
`sched16_boot`. Если маркера нет, таймштамп в RAM становится 0, журнальная
замена очищает только 2048 Б расписаний. Затем одним сохранением config/device
фиксируются маркер и таймштамп 0. До этой фиксации следующий старт повторяет
очистку; после неё новое расписание сохраняется при следующих стартах.
Распознавание не зависит от содержимого старых 32-байтных записей.

При заводской очистке расписаний сначала атомарно сохраняются отсутствие
маркера и таймштамп 0, затем выполняется та же очистка и фиксация маркера.
До фиксации намерения может сохраниться прежнее состояние; после неё старт
обязан завершить очистку. Ошибка чтения/записи блокирует доступ к таблицам через
`table_fault`; ложный маркер в RAM не остаётся. Следующий старт повторяет
восстановление. Регистрация передаёт серверу сохранённый таймштамп 0.

## Расхождения и границы

1. В HEAD нет потребителя `scene[8]`: триггер разблокировки напрямую копируется
   в статус. Исполнение восьми сцен по расписанию ранее не работало; новая
   задача сохраняет это поведение. Проверены хранение и получение сцен из
   общего хвоста. Отсутствующий исполнитель сцен не добавлялся: требование
   сохранить результат существующей логики выполнено переносом getter.
2. Диапазоны часов/минут, blocked/day, scene и onHoliday описаны в протоколе,
   но прежний валидатор команды 14 их не проверял. По требованию сохранить
   прежние проверки добавлены только необходимые новые длина/N и предел
   индекса 64. Новая политика валидации значений не вводилась.
3. Правило CRC 1040 Б является предложением задания и пока не закреплено
   протоколом. Оно изолировано в одной функции.
4. Строка таблицы 308 в выгрузке протокола всё ещё говорит «не более 32
   записей», тогда как строка 314 явно задаёт N=1–64. Это внутреннее
   противоречие выгрузки; реализован числовой диапазон поля N=1–64, совпадающий
   с заданием. Строка 29 ИЗМЕНЕНИЙ и строки 315–339 задают новый размер и хвост.
5. Все проверки выполняются на модели связанного ELF и host-стенде. Проверки
   физической платы, связи с реальным сервером и прошивки устройства не было.

## Итог

205 сценариев в каждом профиле — 0 расхождений. Коммит не создавался.

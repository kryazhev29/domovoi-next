## 3. Новые ID

Общий `table_runtime.c` использует `User/c/table_runtime.inc` во всех вариантах. Предварительно проверяет **весь пакет**: все 32 Б каждой цели равны FF, все входные `reserve[9] != FF`, индексы не повторяются. Любое нарушение оставляет прежний путь через sector journal. `idindex_put` выполняется до ячейки.

Быстрый путь: 31 Б тела → завершение/проверка → отдельный байт 31 → завершение/проверка. Счётчики, hash и конец базы обновляются после подтверждения. После обрыва тело без метки недоступно для прохода; повторная запись такой ячейки требует стирания через журнал. Сырые байты, включая недописанные, остаются частью CRC.

Аудит исходного HEAD:

| Поле cellID_s | Использование до этапа 5 |
|---|---|
| reserve[0..3], смещения 22..25 | `id_first_pass`, `id_set_first_pass`; сохранение в `table_chunk` |
| reserve[4..5], смещения 26..27 | `id_pass_day`, `id_set_pass_day` |
| reserve[6], смещение 28 | `id_time_end`, expiry, сохранение отметки завершения |
| reserve[7..9] | Семантических чтений/записей нет; полное копирование ячейки и CRC включают их |

Проверены именованные обращения `reserve` во всех User C/H/INC и числовые смещения в ID-функциях `User/asm/user_fun_runtime.s`, `User/hybrid/user_fun_hot.s`, index/expiry. Прочие `reserve` относятся к `cellLog_s`, контекстам FW и конфигурации. В старом ASM нет ID-чтения байта 31; встречающиеся word-доступы `#31` принадлежат другим структурам. Серверный пакет копирует резерв как непрозрачные байты — код не гарантирует нули, поэтому условие `!=FF` проверяется явно.

Обновлённые читатели: линейный `user_findID`, `idindex_find` и rebuild, `user_getNumbersCount`, `id_cells_end`, `user_updateID`, expiry и пересчёт после пакета. Общая выгрузка использует соответствующие логические счётчики; физический `id_used_bytes` и service CRC намеренно учитывают недописанные байты. Очистка стирает всю соответствующую область, включая недописанные ячейки.

`test_stage5_id`: 32 позиции обрыва тела с отказом поиска/пересчётом/повтором, 10 промежуточных значений метки, смешанный пакет с поздней грязной целью, 60 программирований без стирания для 30 новых ID, точные входные байты при известном времени. Дополнительно входной FF-маркер проверяется для пустой и прежде занятой цели: обязательно стирание через SJ, логические count/end = 0, физический used = 32 и CRC сырых байтов совпадает. Старые тесты журнала сохраняют сценарии через намеренно непустую цель; это не замена тестов восстановления быстрым путём.

**Контрпример к 20 мс:** 30 × 2 × 0,7 мс = **42 мс busy NOR**, ещё без SPI, проверок, индекса и CRC-метаданных. Он записан в тесте как `target_20ms_feasible_in_existing_model=false`. Предложение: программировать тела нескольких ячеек одной страницей, затем отдельно группу меток, с FF на остальных позициях. Это требует изменения буквального порядка задачи и отдельных power-тестов; без ответа владельца такой вариант не подменял согласованный.

Ещё одно сохранённое ограничение: старый путь через журнал при известном времени меняет `reserve[4..5]` и у нового ID. Быстрый путь сохраняет присланную ячейку полностью. Чтобы оба пути всегда совпадали с сервером по сырым байтам **нового** ID, нужно отдельно убрать инициализацию дня из старого пути только для новой ячейки. Прежнюю политику заменяемых ID здесь не меняли.

## 4. Дифференциальный CRC

`id_crc_cache.c`, `id_crc_io.h`: A/B-секторы `0x1FB000` и `0x1FC000`; 16 Б защищённого заголовка банка и 510 записей по 8 Б `{generation, CRC16, ~CRC16}`. Dirty — запрограммированное поколение с пустой парой CRC. При ротации последняя запись переносится в новый банк, затем дописывается требуемая. Инверсии поколения/магии защищают выбор банка от частичного стирания.

До изменения ID дописывается dirty. Разница старых и проверенных новых байтов считается с seed 0 и продвигается на длину хвоста; итоговый CRC учитывает всю исходную область, включая FF. После завершения транзакции публикуется валидный CRC. При старте dirty/нет значения/недописанная запись означают фоновый полный пересчёт порциями 64 Б; до готовности ответ идёт прежним полным путём. Во время service CRC фон не добавляет задержку каждому его poll.

Все писатели MB_ID проходят общий guard:

| Писатель | Путь |
|---|---|
| Пакет 13 | Общий table runtime: прямые программы либо `sj_runtime` |
| Первый проход, день, cntPass | C/ASM/HYBRID `user_updateID` → `mem_patch[2]` → `mem_replace[_pages]` → sync SJ |
| Expiry | Общий expiry runtime → async SJ |
| Команда очистки | C/ASM idclear → guarded async erase |
| Синхронная очистка ID | `user_clearMemBlock`, `mem_erase_mem` → guarded erase |
| Восстановление в приложении | `sj_io_write/erase`, sync memory wrappers |
| Восстановление старым загрузчиком | Dirty **до** записи заголовка SJ с адресом ID; загрузчик не меняется |

В C guard подключён через общий внутренний заголовок и sector runtime; в активных ASM-вызовах async start/poll/active и sync write/erase заменены общими обёртками. Сам низкоуровневый W25-драйвер остаётся raw для работы guard с метаданными. Новые служебные сектора защищены `mem_reserved`.

Дополнительно найдены и исправлены два контрпримера:

1. Обрыв после SJ_COMMIT, до первого изменения MB_ID: загрузчик при следующем старте восстанавливает данные до запуска приложения. Dirty только перед erase был бы поздним; наблюдался старый CRC **28701** вместо **55989**. Тест `loader_recovery`; dirty теперь предшествует заголовку, разрешающему восстановление.
2. Проверка SJ_COMMIT вернула ошибку, но намерение восстановления уже записано. Нельзя при освобождении владельца публиковать прежний CRC. Тест `failed_commit_recovery`; публикация требует готовых таблиц и подтверждённо пустого SJ_META.

`test_stage5_crc` сравнивает все классы писателей с независимым полным CRC сырых байтов. Power-тест: 42 обрыва dirty/data/valid и ротации A/B, частично стёртое поколение, плюс оба сценария неизменённого загрузчика. Его raw-восстановление моделируется на границе NOR; физический bootloader не исполнялся на плате.

## 2. Кольцо событий

Общие `log_ring.c`, `log_cursor.c`, `log_migration.c`, C upload runtime используются всеми вариантами. Старое начало `0x1CF400` не выровнено; кольцо занимает **`0x1D0000..0x1E7FFF`**, те же 96 КиБ. 24 сектора × 127 записей = **3048**, на 24 меньше прежних 3072.

3048 — максимальная ёмкость. При ротации целиком стирается самый старый сектор: после первой новой записи остаётся 2922 события, затем число снова доходит до 3048; обрыв после erase, до записи оставляет 2921. Это следствие согласованной секторной ротации, а не обещание постоянно хранить 3048 событий.

Первые 8 Б заголовка — magic/seq. В оставшихся байтах первого 32-байтного слота: инверсия seq, предыдущий подтверждённый index с инверсией, число валидных записей закрытого сектора с инверсией, намерение ротации с инверсией. Эти дополнения не отнимают ещё одну запись.

Причины дополнений закреплены тестами: частичное стирание может оставить magic и превратить seq 1 в 129 — один magic/seq ошибочно выбирает старую голову; новая пустая голова должна помнить последний index; частично стёртый хвост с целым старым заголовком нельзя считать живым. Сначала подтверждаются count и намерение ротации, затем erase → защищённый header → magic → body → commit. Неполное тело пропускается.

Старт: 24 заголовка, двоичный поиск конца головы, проверка только её максимум 127 записей. Полное кольцо: **160 чтений / 5104 Б**, вместо 96 чтений / 98304 Б. Та же модель CPU/SPI даёт ASM/HYBRID **260,049 → 16,706 мс**, C **280,784 → 17,653 мс**. Однократная миграция старого формата отдельно требует полного чтения старого журнала; обычный старт после неё полного скана не делает.

Миграция идёт с конца через прежний SJ; намерение хранится в `0x1FD000`. При полном старом журнале сохраняются последние 3048 событий, теряются 24 наиболее старых. После обрыва подтверждённые новые сектора не переписываются, незавершённый восстанавливается SJ. Старый загрузчик не распознаёт адрес журнала событий как ID-назначение и не изменён; миграцию завершает приложение.

Указатели выгрузки/ACK — 32-битные **номера записей** в свободных `device.reserv[16..31]`, существующая структура и пакет сохранены. Указатель публикуется после транзакционного сохранения конфигурации; старые порядковые указатели переводятся при миграции. Если номер уже стёрт, выгрузка начинается с наиболее старой живой записи.

Тесты: две ротации; 35 обрывов ротации; 34 позиции записи body/commit; 36 переходов миграции с обрывом; старые журналы 1/126/127/128/3048/3072; legacy CRC и wire, повреждение CRC, read error; 129 вариантов границы количества/конца. Контрпример указателя: выгрузка начинается **с 129**, после ACK сохраняется **161**, перезапуск это значение сохраняет. Дополнительный точный пример: номер 1 уже отсутствует, стирается сектор с номерами 2–128; устаревший курсор 1 начинает выгрузку с **129, не 257**. Проверка частично стёртого поколения отдельно отвергает ложную голову 129.

При проверке реального `user_init` обнаружены и исправлены старые адресные константы ASM/HYBRID, которые маскировала общая тестовая фикстура. Теперь `real_layout` исполняет production-инициализацию для 2/16 МиБ и проверяет карту до остальных сценариев.

## 6. NOR 2 МиБ

`storage_profile.c` отключает все I/O-операции ID-индекса для кода плотности 0x14 и неизвестных/меньших устройств; линейный поиск остаётся обязательным. RAM-only `idindex_runtime_active` не обращается к NOR. Фото при нулевой области отвечает ошибкой.

Модель обрезает физический backing store до `0x200000`; чтение выше границы возвращает FF, запись/стирание запрещены, попытки учитываются. Проверяются production-карта памяти, пакет 30 ID, поиск карты, журнал и выгрузка, конфигурация, staging FW размером текущего приложения с проверкой всех записанных байтов, отказ фото; дополнительно — старое READY-состояние индекса и прямые вызовы всех публичных index API. До отдельного самотеста границы попыток обращения выше 2 МиБ нет.

Базовых функций, не работающих в этом профиле модели, не обнаружено. Обновление FW проверено до сохранённого образа/ответа, без прошивки микроконтроллера и физического перезапуска.

## Ограничения проверки

- Не выполнена цель 20 мс задачи 3; безопасный буквальный алгоритм оставлен, ускоряющий вариант предложен выше.
- +1% по полному CPU-пути выполнен для возврата чётности и общего завершителя отправки, но не подтверждён для всех серверных путей после добавления механизмов надёжности; контрпримеры и отдельные замеры реального времени модели приведены в разделе 5.
- Прежняя инициализация reserve-дня в journal fallback сохранена; для абсолютного совпадения с сервером у новых ID в обоих путях нужна описанная отдельная правка.
- Промежуточные полные прогоны не все были зелёными: потребовались адаптер общего `packet_send`, ожидания канонического серверного резерва, bounded CRC I/O в моделях и обновление адресации мутаций/старых исходниковых log-тестов. Это не выдано за успешные промежуточные проверки; итог оценивается по окончательному прогону и сохранённым power/mutation-проверкам.
- Все времена — модельные; задержки конкретной NOR, электрические обрывы питания и плата не измерялись. Никаких операций на устройстве или сервере не выполнялось.

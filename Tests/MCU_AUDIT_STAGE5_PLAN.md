## Резервирование внешней flash

Ниже диапазоны включают оба конца. Для пользовательских блоков указаны физические
границы стирания, округлённые к 4096 байтам, а не только занятые байты структуры.

| Область | Физический диапазон | Источник / назначение |
|---|---|---|
| Кандидат FW | `0x000000–0x01FFFF` | `BOOT_CANDIDATE`, `BOOT_SLOT_SIZE` |
| Журнал загрузчика | `0x020000–0x020FFF` | `BOOT_JOURNAL`, отдельный владелец |
| Резерв FW | `0x021000–0x040FFF` | `BOOT_BACKUP`, `BOOT_SLOT_SIZE` |
| ID | `0x041000–0x1C7FFF` | `mem[MB_ID]` |
| Группы | `0x1C9000–0x1C9FFF` | `mem[MB_GROUP]` |
| Расписания | `0x1CA000–0x1CAFFF` | Логические данные начинаются с `0x1CA800` |
| Праздники | `0x1CC000–0x1CCFFF` | `mem[MB_HOLIDAY]` |
| Прежний адрес настроек | `0x1CD000–0x1CEFFF` | Логический образ `0x1CD400–0x1CE3FF` |
| Журнал событий | `0x1CF000–0x1E7FFF` | Логические данные `0x1CF400–0x1E73FF` |
| Временные ID | `0x1E8000–0x1F4FFF` | Логические данные `0x1E8400–0x1F43FF` |
| Банк настроек 0 | `0x1F5000–0x1F6FFF` | Данные + собственный сектор metadata |
| Банк настроек 1 | `0x1F7000–0x1F8FFF` | Данные + собственный сектор metadata |
| **Новый scratch-data** | **`0x1F9000–0x1F9FFF`** | **Полная новая копия одного сектора, 4096 байт** |
| **Новые metadata** | **`0x1FA000–0x1FAFFF`** | **Заголовок транзакции и commit** |
| Свободный остаток ниже фото | `0x1FB000–0x1FFFFF` | В этом этапе не используется |
| Фото, если область включена | `0x200000–0x2FFFFF` | Собственный scratch `0x2FE000–0x2FFFFF` |

Photo scratch занимает последние 8192 байта области фото и в общую транзакцию
не входит.

Предлагаемые два сектора занимают 8192 байта **внешней flash**. Это не экономия ОЗУ.
Они находятся в пределах уже используемого первых 2 МиБ; включение фото и определение
модели микросхемы не меняются.

## Транзакция одного сектора

Разделить независимое от STM32 ядро транзакции и адаптеры W25 приложения/загрузчика.
Общий заголовок закрепляет адреса, формат metadata и допустимые destination.
Работа страницами не требует выделения ещё одного блока 4096 байт.

Metadata: magic, версия, адрес выровненного destination, длина 4096, CRC32
scratch-data, контрольная сумма заголовка и контрольные инверсные поля.
Commit-маркер программируется отдельной последней операцией.
Заголовок без полного commit не разрешает стирание destination.

1. **Восстановить** ранее подтверждённую транзакцию. Пока она не завершена,
   повторно использовать scratch запрещено.
2. **Стереть metadata и проверить весь сектор на `0xFF`**. Только после этого
   можно стирать/перезаписывать scratch-data: остаток старого commit не должен
   разрешить перенос нового незавершённого образа.
3. **Стереть scratch-data**, проверить стирание, записать новый образ 16 страницами
   по 256 байт. Соседние записи и байты вне логического блока сохраняются.
4. **Проверить весь scratch**: чтение, сравнение с подготовленным образом, CRC32.
   Отказ любого чтения/программирования завершает попытку ошибкой до destination.
5. **Записать metadata и commit**, прочитать обратно и проверить заголовок,
   commit и CRC scratch. До этой точки единственная рабочая копия остаётся прежней.
6. **Destination**: стереть, проверить стирание, перенести страницы из scratch.
   При отказе scratch и подтверждённый commit сохраняются для повторного восстановления.
7. **Проверить destination полностью**, включая CRC и сравнение со scratch.
8. **Очистить metadata** только после успешной проверки destination. Стирание
   scratch-data здесь не требуется: следующая транзакция очистит его после metadata.

В каждой длинной операции обслуживать watchdog. Ошибки возвращаются наверх;
`SUCCESS` и обновление timestamp разрешаются после успешного завершения всех
затронутых секторов. При отказе очистки metadata вернуть ошибку и сохранить
возможность повторного recovery, даже если данные destination уже записаны.

До commit после перезапуска должен остаться **целый старый сектор**;
после полного commit recovery обязан получить **целый новый сектор**.
Повторное выключение во время recovery допускается сколько угодно раз:
подтверждённый scratch не очищается до проверки destination.
Сбой стирания metadata при завершении безопасен для уже проверенного destination.

Допустимые destination: физические сектора ID, групп, расписаний, праздников
и временных ID. Проверять выравнивание, диапазон и арифметическое переполнение.
Запрещены boot slots/journal, config slots/legacy, журнал событий, фото,
scratch и незанятые промежутки. Транзакция не должна вызвать публичный `mem_*`
из собственного recovery и рекурсивно войти в себя.

Атомарность — **один сектор**, а не вся команда из нескольких секторов.
Если сбой случился после сохранения первого сектора, он может быть новым,
следующий — старым. Timestamp всей таблицы при этом не подтверждается.

## Интеграция и запуск после сбоя

- `mem_rewrite` для обычных таблиц использует новую транзакцию.
  Имеющаяся отдельная атомарная схема config/device сохраняется.
- Все промежуточные и последние сбросы буфера в командах 13–16 переводятся
  с `erase + write` на тот же механизм. Проверяются пути изменения passCount
  через `user_updateID`, в том числе временные ID.
- Recovery приложения выполняется после задания разметки и до чтения таблиц,
  настроек/пересчёта состояния и запуска обработки доступа.
  При незавершённом recovery повреждённая таблица не используется для допуска;
  новая операция с таблицами получает существующую ошибку выполнения.
  Scratch не очищается из-за ошибки транспорта или flash.
- Необходимая часть B24 в **загрузчике 0x32**: выполнить тот же recovery перед
  запуском любого приложения, включая откат на предыдущую FW.
  Иначе более старая FW без нового recovery может увидеть сектор посреди переноса.
  Для этого добавить отдельные проверяемые storage callbacks; существующие
  границы API записи кандидат/backup остаются прежними. Recovery получает доступ
  только к двум scratch-секторам и перечисленным destination, а не ко всей flash.
  При подтверждённой незавершённой транзакции и ошибке flash запуск приложения
  блокируется; загрузчик остаётся в существующем сервисном режиме без нового
  формата команд/ответов. Не вводить бесконечное блокирующее ожидание recovery.
- В отчёте отдельно перечислить изменения загрузчика: подключение общего ядра,
  storage callbacks с ограничениями адресов, проверка recovery перед переходом
  в приложение. Версия/протокол 0x32, размер области 32 КиБ и адреса приложения
  `0x08008000/0x08008200` сохраняются. Изменение исходников не означает прошивку платы.

Восстановление при автоматическом откате на старую FW требует загрузчика,
содержащего этот recovery. Уже установленный прежний 0x32 его не имеет;
одинаковый номер версии сам по себе не подтверждает наличие функции.
Испытание/установка на плату остаются отдельным действием владельца.

## Тест сначала, затем исправление

1. Добавить регрессионный host-тест настоящего текущего `mem_rewrite`: выключение
   во время erase/program ID-сектора, перезапуск с сохранённой моделью flash,
   проверка полного старого/нового сектора и соседних ID. На текущем коде тест
   должен упасть из-за уничтожения единственной копии; сохранить вывод падения.
   Проверяемый механизм не подменять заглушкой «успешного parser/recovery».
2. Расширить `storage`: резервирование адресов по производственным константам,
   непересечение округлённых блоков, config/boot/photo journals; запрет использовать
   scratch как обычный пользовательский сектор. Изменение разметки должно ломать тест.
3. Для каждого этапа транзакции и recovery моделировать power-cut до/после
   erase, каждой страницы, заголовка, commit, проверки и очистки metadata.
   В erase/program — разрывы по байтам, в commit/header также незавершённые биты.
   Повторные разрывы recovery, старые metadata перед повторным использованием
   scratch, границы destination, соседние неизменяемые байты.
4. Отдельно проверить отказы read/WEL/erase/program/readback, повреждённые
   metadata/CRC, запрет стирать destination без полного commit, сохранение journal
   при незавершённом переносе и запрет новой транзакции поверх него.
5. Проверить настоящие ветки команд 13–16: промежуточный/последний сектор,
   отказ записи, отсутствие `SUCCESS` и изменения timestamp при отказе.
   Проверить `user_updateID`/passCount и восстановление при старте приложения.
6. Проверить общий recovery через адаптер загрузчика: нормальный запуск,
   откат на предыдущую FW, сервисный режим при отказе и повторный старт.
   Проверить, что firmware/backup/config/log/photo ни разу не становятся destination.
7. После исправления — все host-группы, tx во всех пяти сценариях,
   `Bootloader/tests/run_tests.py`; IAR DomovoiNext Release/Release_IPv3,
   DomovoiBoot Release/Modem_Release. Требуется 0 ошибок, новые предупреждения
   отдельно перечислить. Добавить Unicorn-проверку реального IAR-кода recovery,
   стека и выделений heap по образцу имеющихся IAR-тестов.

B24 — один коммит с падавшим регрессионным тестом и всеми связанными изменениями.
Обновление итогового отчёта допускается отдельным документальным коммитом.
Исходники прошивки изменять только скриптом с сохранением cp1251/CRLF;
комментарии — по-русски.

## ОЗУ и границы этапа

База из Release map этапа 4: щель между `__segment_end("HEAP")` и `fault_record`
**56 байт**, CSTACK **4096**, HEAP **5120**. По окончании этапа сравнить свежую
Release map с этой базой; новые размеры брать из IAR map.

Существующие буферы вызывающих функций по 4096 байт пока сохраняются.
Копирование scratch/destination выполняется страницами; новый общий буфер
4096 байт в heap или статической ОЗУ не добавляется. Удаление имеющихся секторных
буферов, разбор UART на месте и отказ от stash относятся к этапу 7.
ICF и резервы CSTACK/HEAP в этапе 5 не уменьшаются.

Без платы не подтвердить реальные частичные erase/program при просадке питания,
задержки и ресурс flash, watchdog при минимальном напряжении, фактический пик
стека с IRQ и переход на восстановленный сектор при аппаратном сбросе/откате.
Power-cut модель и Unicorn проверяют алгоритм, но не заменяют эти испытания.

После согласования плана выполнить только этап 5, дать отчёт
«тест падал → проходит», коммит, поведение, ОЗУ до/после и ограничения;
затем остановиться до разрешения на этап 6.
